**⚠ "66 tables" is 54 BASE TABLES + 12 VIEWS.** `db/migration` head applied to a scratch DB gives
**54 tables, 12 views, 66 relations, 924 columns**. The 924 is right and was always right, but
`information_schema.columns` counts **views**, so anything calling it "66 tables" is mislabelled — and
a view delta is a different severity from a table delta (views are regenerated by the next
`CREATE OR REPLACE VIEW` migration). Report them separately.

**`db/migration` is NOT purely incremental** — `V2.2.00__base_v2_schema.sql` carries the whole
baseline (53 `CREATE TABLE`), V2.2.13 adds one. The separate `db/v1-to-v2-onboarding/schema/` tree
(32 files, V1.0.01→V2.1.17) is the *other* path a tenant can arrive by. Two roots, one runtime
location: `StartupFlywayMigrator.TENANT_LOCATION = "classpath:db/migration"`.

**Recipe.** Apply `src/main/resources/db/migration/V*.sql` in `sort -V` order to a scratch
`postgres:14-alpine` with `psql -v ON_ERROR_STOP=1`, then compare a per-relation fingerprint of
`(column_name, data_type, is_nullable)`. Plain psql is faithful **only because there are 0 Flyway
placeholders** — verified with a positive control (the same grep finds `${` in `.github/workflows`).
Flyway's default is placeholders ENABLED, so if one is ever added psql applies it literally and the
reference silently diverges.

**This is now a script, don't re-derive it:** `src/main/resources/db/verify-tenant-schema-conformance.sh`
(SBDEV-3295). Builds the reference itself, so it cannot go stale; `--from-landlord <conn>` enumerates
tenants; `--self-test` proves all 7 finding classes fire against a deliberately drifted clone.
Read-only against tenants (reference travels as an inline VALUES list — no temp table, no write privilege),
so it is safe to point at PRD.

ShipItEz has **two** UAT warehouses (`c1wh`→`wh01`, `nywh`→`wh02`); an earlier measurement covered
only one, and missed Hydra UAT entirely. ⚠ **And AC-3's "all PRD and UAT tenants" is not the set that
matters for a DEPLOY** — `dev_wh01_om1` is WineCo-derived and the ONLY active tenant in `dev_landlord`,
so a dev deploy is a live rehearsal of any non-no-op migration path. A review lane found that gap;
enumerate dev too whenever the question is "what happens when this ships". Enumerate from landlord `tenant_db_configuration ⋈ tenant
WHERE active`, never from memory. **PRD still has exactly one active tenant** (hydra/nywh).

**Hydra PRD matches despite being 4 migrations behind** — V2.2.22/23/24 are sysprop seeds, V2.2.25 is
`CREATE OR REPLACE FUNCTION`. **Version lag ≠ column drift, and matching versions ≠ matching schemas.**
Check what the gap *contains*.

**WineCo's only real finding is `billoflading.transfer_id` NULLABLE where migrations say NOT NULL**
(plus unused extras `itemdata.archive`, `customerorder_batch.packingline`, and 5 extra tables incl.
`bak_ul292734_20260825`, a hand-made backup that appeared *after* the ticket was filed — the extra-object
set drifts on its own, so date any baseline).

**⚠ ROOT CAUSE — it is inherited from the v1 source DB, so PRD onboarding will REINTRODUCE it.**
Both migration paths declare `NOT NULL` (`V2.2.00` and `V1.0.01__wms_tables.sql`). The v1 sources
disagree: **v1 WineCo `wh01_om1` is NULLABLE**, v1 ShipItEz `wh01_shipitez` is `NOT NULL` — which is
exactly why WineCo v2 is loose and both ShipItEz v2 DBs are clean. The v1→v2 conversion **carries the
v1 column definition forward and never asserts the migration's constraint**. Fixing only
`wh01_om1_v2` (UAT) leaves PRD to inherit it at cutover.

**RESOLVED — `V2.2.26__billoflading_transfer_id_not_null.sql`** (SBDEV-3295 AC-4, approved by Nam
2026-09-10, committed `7ea18760`, **not yet pushed**): `ALTER TABLE public.billoflading ALTER COLUMN
transfer_id SET NOT NULL`. Schema-qualified deliberately — `search_path` is `"$user", public` and app
roles are named `wh01_om1`/`wh03_om1`/`wh01_hydra_v2_app`, so a same-named schema would take
precedence. Safe: 0 NULL on all six DBs and the v1 source; app role **owns** `public.billoflading`
everywhere (it is an ALTER, and ownership drift has frozen Flyway here before). Cost is asymmetric —
`SET NOT NULL` on an already-NOT-NULL column **skips the verification scan** (1.588 ms vs 119 ms over
2M rows measured), so only the loose DBs scan; but the ALTER takes ACCESS EXCLUSIVE and
`StartupFlywayMigrator` builds its own Flyway datasource that never passes through
`tenantTransactionManager`, so **its lock wait is unbounded**. Land it BEFORE the WineCo PRD cutover,
and re-check 0-NULL on the actual source then. Pinned by `BillofladingTransferIdNotNullIT` — a
fresh-migrate test would be **vacuous** (V2.2.00 already declares NOT NULL), so each test replays a
starting shape: migrate to 2.2.25, diverge, migrate to head.

**⚠ `transfer_id` grep trap.** It occurs twice in `V2.2.00` with contradictory nullability and neither
line names its table: `:623` is `advice` (legitimately nullable everywhere), `:679` is `billoflading`
(NOT NULL). Same adjacent pair at `V1.0.01:23`/`:83`. Grepping the column name alone makes the
migration look self-contradictory and the check look wrong.

**Hibernate cannot substitute for this.** `validate` checks only that a MAPPED column exists with a
compatible type — it ignores extra columns/tables and does **not** enforce nullability either way
(see [[hibernate-validate-ignores-extra-columns-and-nullability]]). So do NOT implement schema
conformance by pointing `ddl-auto=validate` at production; nullability is precisely what it cannot see.
Production runs `ddl-auto=none`; the SBDEV-3285 `postgres-integration` lane grades a **pristine**
migrated container, not any tenant's DB.

**Blind spots:** name / `data_type` / `is_nullable` in schema `public` only. **Not** precision or
length (a `varchar(255)` vs `varchar(64)` divergence reads as identical `character varying` —
deliberately out of scope, Nam 2026-09-10), defaults, constraints, indexes, keys, sequences, or
function bodies.
