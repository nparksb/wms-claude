# Mutation testing (PIT) for wms2-api

## Why this exists

Every plan in this vault ships a `verify-<plan-id>.sh` grep script. Across SBDEV-2994 and SBDEV-2995
those scripts were broken **four separate times**, each round closing the previous round's escapes and
each followed by a new lane finding more:

| Round | Result |
|---|---|
| SBDEV-2994 rev 1 | 5 rows passed on wrong implementations |
| SBDEV-2994 rev 2 | 11 self-caught defects; 6 near-misses scored `0 fail` |
| SBDEV-2995 rev 1 | 5 near-misses scored `22 pass / 0 fail` |
| SBDEV-2995 rev 2 | an independent lane found **13 false GREENS and 10 false REDS** |

The worst case: **unfixed code plus one dead helper method** scored every Fix row green, because a
`slice` anchor is a first-match-in-file search and a decoy relocates the graded window.

This is not carelessness. **A regex over source text cannot express "this predicate, in this method,
actually enforces this rule."** It can only express "these tokens appear near each other", and every
such assertion has a decoy. Mutation testing asks the right question instead: *do the tests have
teeth?* — and it is generated by a tool with no model of the fix, so it has none of the author's
blind spots.

## Setup

Add to `v2/wms2-api/pom.xml`, in `<build><plugins>` (verified working 2026-08-19 on Java 21 /
Spring Boot 3.5.9 / JUnit 5.12.2):

```xml
<plugin>
    <groupId>org.pitest</groupId>
    <artifactId>pitest-maven</artifactId>
    <version>1.19.1</version>
    <dependencies>
        <dependency>
            <groupId>org.pitest</groupId>
            <artifactId>pitest-junit5-plugin</artifactId>
            <version>1.2.3</version>
        </dependency>
    </dependencies>
    <configuration>
        <outputFormats><outputFormat>XML</outputFormat></outputFormats>
        <timestampedReports>false</timestampedReports>
        <parseSurefireConfig>false</parseSurefireConfig>
        <jvmArgs>
            <jvmArg>--add-opens=java.base/java.lang=ALL-UNNAMED</jvmArg>
            <jvmArg>--add-opens=java.base/java.util=ALL-UNNAMED</jvmArg>
            <jvmArg>--add-opens=java.base/java.time=ALL-UNNAMED</jvmArg>
            <jvmArg>--add-opens=java.base/java.nio=ALL-UNNAMED</jvmArg>
            <jvmArg>--add-opens=java.base/sun.nio.ch=ALL-UNNAMED</jvmArg>
        </jvmArgs>
    </configuration>
</plugin>
```

## Three gotchas that each cost a debugging cycle

1. **`<parseSurefireConfig>false</parseSurefireConfig>` is mandatory.** Surefire's `argLine` in this
   pom carries jacoco's late-binding `@{argLine}` placeholder. PIT does not resolve it, so the minion
   JVM treats it as an `@argfile` and dies with ``could not open `{argLine}'`` → `MINION_DIED`.
   Because it is skipped, the `--add-opens` flags must be repeated in `<jvmArgs>`.
2. **`pitest-junit5-plugin` must match the JUnit platform.** This repo is on
   `junit-jupiter 5.12.2` / `junit-platform 1.12.2`. Plugin **1.2.1 fails** with
   `TestEngine with ID 'junit-jupiter' failed to discover tests` → `UNKNOWN_ERROR`. **1.2.3 works.**
3. **Compile first.** `mvn test-compile` before the PIT goal, or the pre-scan reports
   `Created 0 mutation test units` and the run fails with "No mutations found".

## Running it

Always scope — a whole-project run is minutes, a scoped one is seconds:

```bash
export JAVA_HOME=~/.sdkman/candidates/java/21.0.11-ms
export PATH="$HOME/.sdkman/candidates/maven/current/bin:$JAVA_HOME/bin:$PATH"

mvn -o test-compile -q
mvn org.pitest:pitest-maven:mutationCoverage \
  -DtargetClasses=net.aim_ai.wms.service.YourService \
  -DtargetTests='net.aim_ai.wms.unit.service.YourServiceUnitTest'
```

Read the survivors — this is the actionable half, and the part no grep can produce:

```bash
python3 - <<'PY'
import xml.etree.ElementTree as ET, glob
f=glob.glob('target/pit-reports/**/mutations.xml',recursive=True)[0]
for m in ET.parse(f).getroot():
    if m.get('status')!='KILLED':
        print(f"{m.get('status'):11} line {m.findtext('lineNumber'):>4}  "
              f"{m.findtext('mutatedMethod')}  ::  {m.findtext('description')}")
PY
```

## Worked example — it found a real gap on the first run

Run against SBDEV-2994's **shipped** `DestinationEligibilityService` (commit `3abb1f22`, PR #167):

```
>> Line Coverage (for mutated classes only): 57/59 (97%)
>> Generated 30 mutations Killed 27 (90%)
```

A good score — those tests do have teeth. The three that got through:

| Status | Line | Method | Mutation |
|---|---|---|---|
| **SURVIVED** | 189 | `gatedViolationReason` | replaced return value with `""` |
| NO_COVERAGE | 195 | `gatedViolationReason` | replaced return value with `""` |
| NO_COVERAGE | 222 | `locationNameOf` | replaced return value with `""` |

The survivor is the **reason token** — the `%2$s` that tells the operator *why* the destination was
refused. No test pins it, so it could be emptied without any test failing. That is the human-readable
half of the error the whole ticket exists to produce, and it was found mechanically in 15 seconds.

Independently, SBDEV-2995's critic review flagged the same thing from the other direction (`%2$s`
undefined for the Nirvana branch). **Two lanes, one finding — one by reading, one by mutation.**

## How mutation coverage maps onto the escapes grep missed

| Escape a grep script accepted | PIT mutator that kills it |
|---|---|
| the `!` dropped — predicate inverted, worse than no fix | `NEGATE_CONDITIONALS` |
| `LOG.warn` instead of `throw` | the removed throw fails a test |
| `assertSourceUnitLoadMovable` with an empty body | `VOID_METHOD_CALLS` |
| guard sysprop-gated, default OFF, inert | the guard line kills **no** mutants |
| assertion-free test stubs | mutation coverage `0%` — precisely what it measures |
| **a dead decoy helper containing a correct guard** | dead code has no covering test; the real line still shows 0 killed |

## What it does NOT solve

Two honest limits, both demonstrated this session:

1. **PIT grades tests, not code.** It is worthless until real tests exist — so the TDD gate comes
   first, not last.
2. **It cannot tell you the fix is aimed at the wrong place.** SBDEV-2995's architect review found
   **3 of 4 proposed sites were wrong** — one unreachable dead code, two already guarded. The verify
   script was checking the wrong thing *correctly*, and a perfect mutation score would have said
   nothing about it. That took an independent reader.

## Adopted position

1. `verify-<plan-id>.sh` is a **coarse "did you touch the right files" check**. Its green is not
   evidence of correctness.
2. **Executed tests are the contract**; mutation coverage on the changed lines is the acceptance
   figure.
3. **Structural claims belong in ArchUnit**, not in a grep. This repo already has five such tests
   (`TransactionManagerArchTest`, `OptionalSafetyArchTest`, `HttpInTransactionArchTest`,
   `ParallelStreamSafetyArchTest`, `PutawayRulesPurityArchTest`). ArchUnit reads **bytecode**, so it
   is immune to formatting, to `this.` prefixes, and to decoys — a dead method is not in the call
   graph. Rules like *"no method may call `transferUnitLoadToCarrier` without first calling the
   eligibility check"* and *"`updatePallet` must carry `rollbackFor` naming both checked types"* are
   natural ArchUnit conditions and impossible regexes. ⚠ `mvn test` **mutates** the tracked
   `src/test/resources/archunit_store` — revert it before committing.
4. **A verify script is never validated by its own author.** Demonstrated four times; the author's
   mutation family only tests what the author already imagined.
