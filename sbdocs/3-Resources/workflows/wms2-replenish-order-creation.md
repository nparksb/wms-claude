# Replenish Order Creation

This document traces every code path that results in the creation of a `Replenishorder` entity. All statements reference actual implementations—no assumptions were added.

## Triggers That Request a New Order

- **Scheduled pipeline** – `ReplenishOrderJob` runs via cron (per-tenant `20 <REPLENISHMENT_TIMER_MINUTE> <REPLENISHMENT_TIMER_HOUR> * * *`, both defaulting to `*`, i.e. every minute — `deriveSpecForCurrentTenant`, `ReplenishOrderJob.java:218-231`; registered by `SchedulingConfiguration.configureReplenishGroups`, `:986`) on the `runFor(TriggerSpec)` path (all tenants whose own schedule matches the firing trigger) or on demand via `runForCurrentTenant()` (the caller's tenant only). ⚠ **Updated 2026-09-06 (SBDEV-3198):** the single `doCalculation(Boolean isCronJob)` entry point this bullet used to name was **deleted** 2026-09-03 and the `isCronJob` flag no longer exists. Both paths check `SYSTEM_PROPERTY_NEW_CRON_JOB_ACTIVATED_KEY` and `SYSTEM_PROPERTY_REPLENISHMENT_TIMER_ACTIVATED_KEY` per tenant and skip that tenant if either is disabled (`ReplenishOrderJob.java:312-313` on the scheduled path, `:424-425` on the manual path, at `df30fa62`; before that check each tenant also takes the per-tenant advisory lock `JobLockId.REPLENISH_ORDER` = `100002L`, keyed with `tenant_db_configuration.id`, `:304`/`:418`, `AdvisoryLockService.java:256`). Once enabled, the package-private `replenish(String tenantName)` (`:453`) runs, in order: `releaseExpiredReplenishClaims` (SBDEV-3626 — puts abandoned STARTED handheld claims back to PROCESSABLE; sysprop `REPLENISHMENT_CLAIM_TIMEOUT_SECONDS`, `<= 0` disables), `mergePickingOrders`, `deleteEmptyFixAssignmentWithoutStockToReplenish`, `cancelUnreachableReplenishment`, `cancelReplenishmentIfFlowbinIsFull`, `generateReplenishmentForItemDataWithoutFixedAssignment`, `generateReplenishmentForItemDataWithFixedAssignmentWithOrders`, `triggerRegularReplenishment`, `updateReplenishmentOrderPriority` (sub-ops 6a/6b, bulk priority updates only) and `recalculateReplenishmentOrderWithoutFixedLocationAssignment`; then a per-item `recalculateForItem` over the touched items and, every cycle, `recalculateOpenOrders(false)` (SBDEV-3624). The paged drain steps read `REPLENISHMENT_PAGE_SIZE` (default 1000) and `REPLENISHMENT_PAGE_LIMIT` (default 100) (`:675-681`); the claim timeout defaults to 600 s (`WmsConstants.java:1476`). The steps that actually create orders are described below.

- **Manual/mobile request** – `/v3/replenish/requestAmount` accepts a `ReplenishMobileOrderDto` payload and forwards it to `MobileReplenishService.requestReplenish` (`src/main/java/net/aim_ai/wms/controller/mobile/ReplenishController.java:108-143`). The service resolves the client (`clientNumber`; an unknown number or one outside the caller's client scope throws `EntityNotFoundException`, SBDEV-3668/3619), item (`itemNumber` scoped to the client), destination location (`destinationLocationName`), and requested quantity (`amountRequested`) and then calls the 3-arg `ReplenishGeneratorService.calculateOrder` (`src/main/java/net/aim_ai/wms/service/mobile/MobileReplenishService.java:464-488`). A missing item, or `calculateOrder` returning `null` (idempotency skip), makes `requestReplenish` return `null`, which the controller reports as the `MsgNoReplenishOrder` error; other exceptions (missing location, a `FacadeException` from `calculateOrder`) are surfaced in the HTTP 200 `{errors:[…]}` envelope, except `DataIntegrityViolationException` (active-duplicate index lost to a concurrent create), which is rethrown and mapped to a retryable 409 by `MobileEndpointExceptionHandler`.

- **Service-level creation** – `ReplenishorderService.create` is used by administrative flows. It mirrors the mobile path: resolve client/item/destination from `ReplenishMobileOrderDto`, then call the 4-arg `calculateOrder` while also passing the DTO’s priority (`src/main/java/net/aim_ai/wms/service/ReplenishorderService.java:112-149`). Unlike the mobile path it first refuses any non-System caller (a caller confined to one client gets `EntityNotFoundException` for the client, SBDEV-3974 tripwire, `:114-119`).

- **Auto-refill after finishing** – ~~`/v3/replenish/checkDestination` invokes `MobileReplenishService.finishReplenishmentOrder`~~ (endpoint and method removed by SBDEV-3638, merged 2026-10-02, `f839921e`). Now `POST /v3/replenish/multi-unitloads` (`fulfillMultipleUnitLoads`) finishes each order via the private `finishReplenishmentOrderWithoutRefill` (no refill) and then, after the commit, best-effort recalculates only the confirmed order's item (`replenishmentOrderMaintenanceService.recalculateForItem`). ~~and then runs one best-effort `replenishGeneratorService.refillFixedLocations()` after the commit~~ ⚠ **Corrected 2026-10-07 (SBDEV-3678, merged to develop as `969882a8` on 2026-10-07)** — the confirm no longer refills or runs the whole-warehouse `recalculateOpenOrders(true)`; refills are left to the replenish cron (every minute). Historical text (anchors below point at the removed code, not at `df30fa62`): it finalizes the current order and then immediately calls `replenishGeneratorService.refillFixedLocations()` (`src/main/java/net/aim_ai/wms/controller/mobile/ReplenishController.java:155-199`, `src/main/java/net/aim_ai/wms/service/mobile/MobileReplenishService.java:359-425`). That refill run could create new `Replenishorder` entities as soon as an operator puts stock away; it no longer does (verified 2026-11-11: `fulfillMultipleUnitLoads`, `MobileReplenishService.java:925-936`; `ReplenishController.java:256-271`). Refills now come only from the replenish cron — by default every minute, since `REPLENISHMENT_TIMER_MINUTE`/`_HOUR` default to `*`.

In every case above, the actual order calculation work happens inside `ReplenishGeneratorService`.

## How Shortages Are Detected Before Creation

- **Fixed locations needing refill** – `FixLocationAssignmentRepository.getRefillFixedLocations` returns assignments where (1) the unit load linked to the assignment holds less stock than the assignment’s lower bound, (2) the assignment is active, (3) no open (`state < FINISHED`) `Replenishorder` exists whose `requestedlocation_id` equals the assignment’s `assignedlocation_id`, and none exists for the same item — since SBDEV-3153 this is two separate `NOT EXISTS` clauses rather than one with an `OR`, which is equivalent but lets Postgres use an index (note the location clause matches the order’s `requestedlocation_id`, not its `destination_id`), and (4) there exists at least one usable source stock unit for the item: `entity_lock = 0`, `amount > 0`, `reservedamount = 0`, unit load / location / area all `entity_lock = 0`, area `useforreplenish = true`, location neither a staging nor a transfer lane (SBDEV-3654), and not inside the manual-cut cooldown (SBDEV-3636: `REPLENISH_MANUAL_CUT_COOLDOWN_MINUTES`, default 60, max 1440, `<= 0` disables — `ManualCutCooldown`, `StockunitRepository.MANUAL_CUT_COOLDOWN_EXCLUSION`) (`src/main/java/net/aim_ai/wms/repo/jpa/FixLocationAssignmentRepository.java:204-234`, the `REFILL_ELIGIBILITY_FROM_WHERE` constant, exposed as `getRefillFixedLocations` `:237` and `getRefillFixedLocationIds` `:241`). The cron consumes the **id** list: `ReplenishOrderJob.triggerRegularReplenishment` (`:837-856`) calls `ReplenishOrderJobService.getRefillFixedLocationIds` (`:270`) and then `refillFixedLocationAssignment(flaId)` (`:276`) per id, which delegates to `ReplenishGeneratorService.refillSingleFixedLocation` (`:118-126`, `REQUIRES_NEW`): it loads the assigned unit load, calculates the missing amount as `upperBound - stockunitList.get(0).getAmount()`, and calls `calculateAutomaticOrder` (not `calculateOrder`) with the assignment’s item and destination. `ReplenishGeneratorService.refillFixedLocations` (`:86-110`, same maths in one loop) and `ReplenishOrderJobService.triggerRegularReplenishment` (`:212`) still exist but have **no caller in `src/main`** (grep 2026-11-11; only unit tests call the latter).

- **Items that lack a fixed assignment** – `ReplenishOrderJob.generateReplenishmentForItemDataWithoutFixedAssignment` gathers item IDs that simultaneously (a) have customer-order demand in state `RAW_ON_HOLD_NO_FIXED_ASSIGNED_LOCATION` (order state below ASSIGNED, `pickingDate <= now`, `markAsVisited = true`, PICK_PACK batch) before their assigned orders are released, (b) lack any fixed location assignment, (c) do not already have an open `Replenishorder`, (d) have no stock in a picking-enabled area, and (e) do have stock in a replenishment-enabled area that is not a staging/transfer lane; the item must also be unlocked (`itemData.entity_lock = 0`) (`src/main/java/net/aim_ai/wms/schedulejob/ReplenishOrderJob.java:773-805`, `src/main/java/net/aim_ai/wms/repo/jpa/ItemdataRepository.java:56-131`, paged query `getIdsForItemDataWithoutFixedAssignmentPage`). The calculated upper bound is the tenant sysprop `FIX_LOCATION_ASSIGNMENT_DEFAULT_VALUE_UPPER_BOUND`, with an absent or unparseable row meaning **84** (`WmsConstants.java:1383-1384`, SBDEV-3998). The service forwards the item ID, that upper bound, and a `null` destination to `calculateAutomaticOrder` (`src/main/java/net/aim_ai/wms/service/job/ReplenishOrderJobService.java:100-111`).

- **Fixed assignments referenced by open orders** – `ReplenishOrderJob.generateReplenishmentForItemDataWithFixedAssignmentWithOrders` walks every active fixed assignment that has picking demand (unassigned PICK_PACK order positions with `pickingDate <= now`, `markAsVisited = true`, where `upperBound > su.amount`, no open `Replenishorder` for the item, and `sum(cop.amount) + reservedAmount > su.amount`; `ReplenishorderRepository.java:333-379`, `getIdsForItemDataWithFixedAssignmentWithOrdersPage`) and delegates to `ReplenishOrderJobService.generateReplenishmentForItemDataWithFixedAssignment` (`src/main/java/net/aim_ai/wms/schedulejob/ReplenishOrderJob.java:807-835`). That service validates the fixed assignment (exactly one stock unit on the assigned unit load, unit load located at the fixed location, labels matching, assignment active, etc.), computes `required = upperBound - amountOnLocation`, and, if the amount on location is below the assignment’s middle bound, again invokes `calculateAutomaticOrder` with the fixed location ID (`src/main/java/net/aim_ai/wms/service/job/ReplenishOrderJobService.java:114-209`; the amount-on-location check is `amountOnLocation >= middleBound` → no replenish).

- **Regular top-off** – After the specialized generators above, the job runs its own private `triggerRegularReplenishment` (`ReplenishOrderJob.java:837-856`), which reuses the eligibility query described in the first bullet through `getRefillFixedLocationIds` + `refillFixedLocationAssignment` (`ReplenishOrderJobService.java:270-278`). It no longer calls `ReplenishOrderJobService.triggerRegularReplenishment()` or `refillFixedLocations()` (see the first bullet).

## Order Calculation and Persistence

`ReplenishGeneratorService.calculateOrder(Long, BigDecimal, Long, Integer, boolean automatic)` (`src/main/java/net/aim_ai/wms/service/ReplenishGeneratorService.java:228-333`, `REQUIRES_NEW`) is the single place where a `Replenishorder` object is instantiated and persisted, regardless of which trigger called it. Callers reach it through wrappers: the 3-arg `calculateOrder` (`:151`, mobile request; priority `PRIORITY_LOW`), the 4-arg `calculateOrder` (`:219`, admin create; caller’s priority; `automatic = false`) and `calculateAutomaticOrder` (`:162`, every cron path: `refillSingleFixedLocation`, `generateReplenishmentForItemDataWithoutFixedAssignment`, `generateReplenishmentForItemDataWithFixedAssignment`; priority `PRIORITY_LOW`, `automatic = true`). The 3-arg and automatic wrappers go through `createIdempotently` (`:172`), which turns a lost race on the `idx_replenishorder_active_item*` unique index into a `null` return.

**Pre-checks before step 1 (SBDEV-4031 / SBDEV-4067):** (a) when `automatic` and a destination is given, the item’s fix assignment at that destination is locked (`fixLocationAssignmentRepository.lockIdByItemdataIdAndLocation`); if no row is found the method logs and returns `null` (`:233-238`). (b) when **not** automatic and a destination is given, an operator create into a location fixed for a *different* item throws `BusinessException("<location> has different fixed assignment")` (`:243-252`); a location with no fix assignment (SBDEV-2854) and the item’s own assignment stay allowed.

**Idempotency check (added SBDEV-2690, guard originally commit `a6b8d6bf`):** after the amount validation (step 1) and before the stock search, `calculateOrder` calls `findBlockingPendingOrder(itemDataId, destinationId)` (`:143`, `:261`) — if a replenish order in state `< FINISHED` already exists for the same item **and** destination, the method returns `null` without creating anything. Scheduled-job / mobile / refill callers treat this `null` as "nothing to replenish today"; the admin `create` path converts it into an HTTP 409 (see caller notes below).

The method then performs the following deterministic steps:

1. **Validation** – load the `Itemdata` row for `itemDataId` and reject non-positive `amount` values with a `FacadeException` (`:253-258`).
2. **Source stock search** – query `stockunitRepository.getStockUnitsByNotLockedAndItemIdAndUseForDeepStorage` twice: first against non-deep-storage areas, then (if nothing is found) against deep-storage areas (`:270-274`). Each row returns a stock unit ID and its amount for a stock unit with `amount > 0` and `reservedamount = 0` whose unit load, location and area are all unlocked, in an area with `useForReplenish = true`, not on a staging/transfer lane, and — for `automatic` creates only — not inside the manual-cut cooldown; ordered by `su.amount, su.created` (`src/main/java/net/aim_ai/wms/repo/jpa/StockunitRepository.java:354-369`).
3. **Stock selection** – pick the first candidate whose amount is >= the requested `amount`; if none qualify, fall back to the first candidate in the list. Fetch the `Stockunit` and its `Unitload` for later use.
4. **`Replenishorder` population** – set the following fields before persisting via `replenishorderRepository.save`:
   - `id`/`number`: `id` comes from the entity’s `@GeneratedValue` sequence `seqentities` (`AbstractBaseEntity`; there is no `getNextId()` any more); `number` is `REPL%06d` from `BasicService.generateReplenishNumber()` over sequence `REPLENISH_ORDER` (`src/main/java/net/aim_ai/wms/service/ReplenishGeneratorService.java:311`, `src/main/java/net/aim_ai/wms/service/BasicService.java:125-131`).
   - `clientId` and `itemdataId`: copied from the selected `Itemdata`.
   - `requestedlocationId`: the storage location of the source unit load.
   - `destinationId`: whatever was supplied by the caller (can be `null`).
   - `requestedamount`: the smaller of the caller’s `amount` and the amount currently on the chosen stock unit.
   - `stockunitId`: the chosen source stock unit.
   - `state`: initialized to `WmsConstants.State.PROCESSABLE`.
   - `prio`: caller-provided priority (admin create) or `WmsConstants.Priority.PRIORITY_LOW` (= 0) for the 3-arg and automatic wrappers. (`PRIORITY_VERY_LOW` no longer exists in `src/main`.)
   - Administrative fields such as `manuallyoverridepriority=false`, `entityLock=0`, and `sourcelocationname` populated from the source location.
5. **Reservation** – the order is saved and flushed (so an active-duplicate unique-index violation surfaces inside this `REQUIRES_NEW` transaction, `:326-327`), then the requested amount is reserved on the chosen stock unit by calling `stockUnitBusinessService.changeReservedAmount` with the `CODE_REPLENISHMENT_CREATED` reason and the order number (`:329`). This locks the inventory for the newly created order.
6. **Return** – hand the fully populated `Replenishorder` entity back to the caller; callers then transform it into DTOs or continue with their own workflows.

If no suitable stock unit exists, the method throws a `FacadeException` ("No replenish stock available with  destination = …") instead of creating an order (`:276-284`).

## What Each Caller Does With the Result

- **Mobile request** – After `calculateOrder` succeeds, `MobileReplenishService.requestReplenish` materializes a fresh `ReplenishMobileOrderDto` using `setOrderToReplenishMobileOrder` and returns it to the device. This DTO includes the source location/unitload, requested quantity, state, and optional destination so the operator can begin scanning immediately (`src/main/java/net/aim_ai/wms/service/mobile/MobileReplenishService.java:464-488`; the DTO mapper `setOrderToReplenishMobileOrder` starts at `:491`, and `readAddOn` adds the destination assignment’s bound only when it is visible to the caller’s client scope).

- **Scheduled job** – The job has no further action on the created order after `calculateAutomaticOrder` returns; orders sit in the PROCESSABLE state until devices pick them up. Its later steps do touch open orders, though: `recalculateReplenishmentOrderWithoutFixedLocationAssignment` (R3, `ReplenishOrderJob.java:917-933` → `ReplenishOrderJobService.java:261-267` → `ReplenishorderService.java:459`) gives every open order (`state <= PROCESSABLE`) that has **no destination** its item’s active fixed location via `assignFixedDestination` (`:485-511`, one `REQUIRES_NEW` transaction per order, skipped when another open order already targets that item at that location); and the per-item `recalculateForItem` loop plus the every-cycle `recalculateOpenOrders(false)` re-derive amounts/sources of open orders (`ReplenishOrderJob.java:504-528`). None of these create orders.

- **Administrative service** – `ReplenishorderService.create` relays a successfully created `Replenishorder` back to its caller. When `calculateOrder` returns `null` (idempotency skip), `create` re-reads the blocker via `findBlockingPendingOrder` and throws `DuplicateReplenishmentException` naming it (`ReplenishorderService.java:137-145`); `ReplenishOrderController.create` (`POST /v3/replenishOrder/create`, `@RequiresFunction(WEB_UI_ACTION_MANAGE_REPLENISHMENT_ORDER)`, `ReplenishOrderController.java:276-303`) catches that and returns **HTTP 409** with an `{errors:[…]}` body — instead of the previous silent HTTP 200 with an empty body (SBDEV-2690). A `DataIntegrityViolationException`/`UnexpectedRollbackException` that is the active-duplicate index makes `create` return `null` directly (`:131-136`), which the controller then returns as an HTTP 200 with a null body (no `errors`; no `ResponseBodyAdvice` exists in `src/main/java`, grep 2026-11-11) — i.e. this concurrent-loser path is still a silent 200, unlike the 409 above. A `BusinessException` (e.g. SBDEV-4067 "has different fixed assignment") is returned as a 200 `{errors:[Business Error]}` envelope.

With these components combined, every path that creates a new replenish order is fully documented and traceable to concrete code locations.
