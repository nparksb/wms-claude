# Lane 1 - Transaction boundary and propagation correctness
Target: wms2 develop df30fa62, src/main/java (read-only). All paths relative to src/main/java/net/aim_ai/wms.
Method: enumerated every `@Transactional` / `@TenantTransactional*` annotation with a script (277 annotation lines, 1 class-level
tenant + 1 class-level landlord), extracted the method signature that follows each, then grepped/scripted for self-invocation,
readOnly writers, checked-exception holes, catch-and-swallow, controller multi-service handlers. Callee bodies read where stated.

Checked exceptions (verified by `extends`): BusinessException, FacadeException (and ToteTeardownException, RequestRefusedException
via them), DuplicateReplenishmentException, ApiException family (ApiInvalidParameterException, ApiMissingUserException,
ApiConstraintViolationException, Sso*), WebserviceBusinessExceptionClientSide. Unchecked: EntityNotFoundException, TenantException,
PutawayConfigValidationException, ClubRunLeaseLostException, WebserviceBusinessExceptionServerSide.

## Summary: this layer is largely clean; the codebase has been hardened repeatedly (SBDEV-3244/3250/3854/4031 comments).
New, verified findings are mostly NON-ATOMIC CONTROLLER SEQUENCES (item 8) plus two latent rollback-only traps.

## FINDINGS

### F1 [Med / conf Med] FixLocationAssignmentController.upadteFixedAssignment: 4 separate commits, non-idempotent toggle, order-dependent validation
File: controller/FixLocationAssignmentController.java:65-90 -> service/FixLocationAssignmentService.java:282-330 (adjustLower/Middle/UpperBound, each its own @Transactional), :669 (changeActive, NO @Transactional, plain save, TOGGLES).
Read callee bodies: yes.
Path: handler runs `changeActive` (if "active" key present), then `adjustLowerBound`, `adjustMiddleBound`, `adjustUpperBound` (each if present). No transaction around them; each commits alone.
Scenario A (partial + non-idempotent): body {id, active:true, lowerBound:<invalid>}. changeActive flips active and commits; adjustLowerBound throws BusinessException -> response "errors". Operator fixes the value and resubmits the same body: changeActive flips active BACK. The UI shows an error yet state changed, and a retry silently undoes it.
Scenario B (validation vs commit order): body raises all three bounds, e.g. (10,20,30)->(50,60,80). adjustLowerBound(50) validates against the OLD middle(20) and is refused ("Lower bound must be lower or equal than middle bound") although the final triple is valid; lowering all three works only in lower->middle->upper order. Either way a multi-field update cannot be applied atomically.
Fix: one @TenantTransactional service method taking the full {active?, lower, middle, upper} and validating the final triple; make "active" a set (value) not a toggle.
Not verified: whether the web UI really posts all fields in one request (comment on the handler says `{ id, lowerBound, middleBound, upperBound }`).

### F2 [Med / conf Med] UserController.createUser: Keycloak user created, then WMS write fails -> permanent "User already exists"
File: controller/UserController.java:~368-405 (createUser), 323-355 (importUser), 427+ (updateUser).
Read: yes (controller); userService.create is @TenantTransactional-class method (UserService.java:221) - failure modes not enumerated.
Path: keycloakService.findUserByUsernameOrEmail -> createSingleUser (external, committed) -> userService.create (tenant tx). Only ApiMissingUserException/SsoCreateUserException/ApiInvalidParameterException are caught. Any RuntimeException or DB failure in userService.create (unique name/number race, sequence, lock timeout) -> 500, the Keycloak identity persists with no WMS user. Retry hits `keycloakUser != null` -> "User already exists with the username or email"; only manual Keycloak cleanup or the separate importUser endpoint recovers.
Also updateUser: Keycloak identity updated first, WMS save second; if save fails Keycloak and WMS disagree (name/email). importUser: WMS row committed, then addUserToWmsGroup can fail -> user exists without group (retry is OK, update branch).
Fix: compensate (delete the Keycloak user) on WMS failure, or create WMS row first inside a tx and call Keycloak in afterCommit with retry; at minimum make createUser fall through to the WMS create when Keycloak user exists but WMS user does not.

### F3 [Low-Med / conf Med] PrinterController.deletePrinter / setDefault: multi-write, no transaction
File: controller/PrinterController.java:~157-190 (deletePrinter), ~192-215 (setDefault).
Read: yes. FKs to printer verified in schema: only client.printerreceiving_id and mywms_user.printer_id (V2.2.00__base_v2_schema.sql:4746,5698).
deletePrinter: per-user `save` (each commits), `clientRepository.updatePrinterToNullByPrinterId` (own tx), `deleteById`, then reassign default (another save). A concurrent user/client pointing at the printer between the null-out and the delete, or an OptimisticLockingFailure on one user save mid-loop, leaves some users/clients detached and the printer still present (500), or the printer deleted with no default of its type. `printer.getProcessdefault()` is read after delete (NPE if column null) - the delete is already committed.
setDefault: two saves in two transactions; window with zero default for the type; failure of the second leaves none.
Fix: move into one @TenantTransactional service method.

### F4 [Low / conf High] ReceivingController.setPallet: createPallet commits, updatePallet separate tx
File: controller/ReceivingController.java:~193-240 (setPallet; same shape at the 243+ handler), service/ReceivingService.java:1099 (createPallet, no tx), :1007 (updatePallet, own tx).

### F5 [Low-Med / conf Med] ClubLineController.activeBatch: assign-lane and activate are separate commits; a failed second step strands the batch at 525
File: controller/ClubLineController.java:158-185; service/CustomerorderBatchService.java:415 (requireNotYetActivated), :423 (activateOrderBatch, no tx), :1245 (assignStagingLaneToOrderBatch, own tx).
Read: yes. State constants WmsConstants.java:97-107: ORDER_BATCH_ACTIVATED=520, STAGING_LANE_ASSIGNED=525.
assignStagingLaneToOrderBatch commits state 525 + staging lane; activateOrderBatch then writes 520 (a NUMERICALLY LOWER state, a rewind by design per the comment at :415). If the second write fails (lock/DB error), the batch is 525 with a lane, and the retry is refused by requireNotYetActivated (`state >= 520` -> "already active"), so the operator cannot re-run activation from this endpoint.
Fix: one tx service method doing guard + assign + activate.

### F6 [Low-Med / conf Med, PLAUSIBLE trigger] ReplenishOrderJobService.cancelReplenishmentOrder: swallowed FacadeException poisons its own REQUIRES_NEW tx
File: service/job/ReplenishOrderJobService.java:303-324 -> service/ReplenishorderService.java:396 (cancelReplenishmentOrder, @Transactional rollbackFor=FacadeException, REQUIRED).
Read: both bodies and callers (schedulejob/ReplenishOrderJob.java:694,719, which catch Exception and LOG.error).
Mechanism (instance of the SBDEV-3854 trap, not previously listed for this method): the job method is REQUIRES_NEW with no rollbackFor; it calls replenishorderService.cancelReplenishmentOrder (joins that tx, rollbackFor FacadeException) and `catch (FacadeException e) { LOG.info }`. A FacadeException thrown inside marks the shared tx rollback-only, the swallow returns normally, and the commit throws UnexpectedRollbackException. The caller logs a generic error; the FacadeException text is only logged when basicService.showLog().
Trigger likelihood: low - HeldShareRelease.release pre-guards the changeReservedAmount failure cases (HeldShareRelease.java:30-55) and the method pre-checks state. Remaining throw sources: "Cannot remove active order" (guarded above), changeReservedAmount internals. Effect when it fires: order never cancels, is re-selected by drainPageZero every tick.
Fix: drop the catch (let it propagate to the job loop) or add rollbackFor to the job method and rethrow.

### F7 [Low-Med / conf Med, PLAUSIBLE] ReplenishmentOrderMaintenanceService swallows FacadeException from joined changeReservedAmount
File: service/ReplenishmentOrderMaintenanceService.java:921-924 (updateRequestedAmount, `return`), :1025-1031 (releaseReservation, LOG.error only); callee service/StockunitBusinessService.java:661 (rollbackFor Business+Facade).
Read: yes. Both callers run in recalculateOrder (REQUIRED, own tx on the cron path via self.; shared tx on the recalculateForItem path). The same file documents the identical hazard as "ACCEPTED" at :760-775 (redirectSource) but these two sites carry no such note and CONTINUE doing work (releaseReservation's caller goes on to markCancelled / save) after the shared tx is already rollback-only. Cron path: UnexpectedRollbackException at that order's commit, caught by the per-order catch in recalculateOpenOrders (:141) - silent skip, repeats every tick. recalculateForItem path: poisons all sibling orders of that item (the exact scenario its :176-190 comment warns about) because its catch only rethrows SQL-cause DataAccessExceptions.
Mitigation present: pre-guards at :905-915 make the throw rare. Rate low unless data is inconsistent (reserved > amount).
Fix: treat the FacadeException as fatal for the unit (rethrow) instead of logging and continuing.

### F8 [Low / conf Med, PLAUSIBLE] In-transaction @CacheEvict can evict before commit (stale re-warm until TTL)
File: service/PutawayConfigService.java:229-233 (setWarehouseDestination, @TenantTx + @CacheEvict on same method), service/SyspropService.java:64-65, LocationService (3 sites); 33 @CacheEvict/@CachePut sites total.
Read: yes for PutawayConfigService/SyspropService; advisor order NOT verified (StartApplication.java:27 @EnableTransactionManagement and config/CacheConfig.java:23 @EnableCaching both default to LOWEST_PRECEDENCE, relative order undetermined statically). If the cache advice is inside the tx advice, eviction fires before commit and a concurrent reader re-caches the old value for the 2-5 min TTL. SdrCacheEvictionEventHandler.java:100-120 explicitly acknowledges "every existing in-transaction @CacheEvict" and declines TransactionAwareCacheManagerProxy, so this is a known choice; listing it because it is the only boundary-ordering exposure for the service-layer writers.
Fix: set order on @EnableCaching so the evict wraps the tx advice, or evict in afterCommit.

### F10 [Low, KNOWN-PATTERN, pool pressure] REQUIRES_NEW nesting holds 2-3 tenant connections per iteration
File: service/job/ReplenishOrderJobService.java:211 (triggerRegularReplenishment REQUIRES_NEW, loops all refillable FLAs) -> ReplenishGeneratorService.java:117 (refillSingleFixedLocation REQUIRES_NEW) -> self.calculateAutomaticOrder (:162, no tx) -> self.calculateOrder (:227 REQUIRES_NEW). While calculateOrder runs: connection 1 (suspended outer, idle), 2 (suspended refill, idle: it only did reads), 3 (active). Default per-tenant Hikari max is 5, 30 s connection timeout (landlord/config/TenantDynamicRoutingDataSource.java:200-203). Two concurrent runs plus request traffic can exhaust the pool; this is the boundary-map "REQUIRES_NEW x29 pool pressure" item, here as a concrete 3-deep chain. Also: ReplenishOrderJobService.java:80,100,114 wrap calculateAutomaticOrder in a REQUIRES_NEW that does nothing the inner REQUIRES_NEW does not (no locks held, so NO self-deadlock - verified, outer only reads).
Other outer-tx + REQUIRES_NEW inner (2 connections): MessageService.createMessage->createServiceLog (now via self., fixed), SequenceTransactionService.getNextSequenceNumber from inside any tenant tx (label/number mint). No self-deadlock found: the sequence row is only touched in the REQUIRES_NEW tx (outer never holds it).
Fix: drop the redundant REQUIRES_NEW on the three ReplenishOrderJobService wrappers and on refillSingleFixedLocation (inner calculateOrder already isolates).

## Positive observations
- The `self` proxy idiom and the `WARNING: keep plain this. call` comments are consistent where they matter (ReplenishmentOrderMaintenanceService, MessageService, ReplenishGeneratorService).
- MANDATORY used for audit/outbox rows so they commit with the change (OutboxService, PutawayConfigAuditService, createServiceLogInCallerTx).
- The `rollbackFor` meta-annotation exists and the dominant convention is explicit; no checked-exception hole in any REQUIRED method.
