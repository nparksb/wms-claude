# Lane 4 - scheduled jobs, async, threads, transaction length
Scope: scratchpad/wms2-develop/src/main/java (detached origin/develop df30fa62). Read-only. All paths below are relative to `net/aim_ai/wms/`.
Docs read first: wms2-scheduled-jobs-catalog.md (section 2 lock ids), transaction-osiv-boundary-map section 10. Landlord DB MCP probe (pg_settings) failed (connection closed), so DB-side settings are UNVERIFIED.

## Findings

### F1 [MEDIUM, PLAUSIBLE] Session advisory lock can be returned to the pool still held when unlock() hits an SQLException
- `service/AdvisoryLockService.java` unlock(long) ~L115-141 and unlock(long,long) ~L221-250: the SQLException catch only logs; the finally always does `conn.close()` (return to Hikari). Session-level `pg_advisory_lock` survives on the pooled physical connection. `pg_advisory_unlock` returning false is also only WARNed.
- Scenario: statement-level failure on the unlock query (cancel, transient error) on a connection that stays usable -> lock stays held by an idle pooled connection until Hikari retires it (maxLifetime, default 30 min). Every replica's tryLock for that (job, tenant) returns false -> the job silently stops running for that tenant for up to ~30 min (trace-level log only). Same replica can even re-acquire (reentrant), masking it on one pod.
- Fix: on unlock failure `conn.unwrap(PGConnection)`/`abort()` or close the physical connection (evict) instead of returning it; or `pg_advisory_unlock_all()` in finally.
- Callee bodies read: yes (whole class). Not reproduced.

### F2 [MEDIUM, PLAUSIBLE - needs landlord GUC check] Lock-holding landlord connection sits idle-in-transaction for the whole job
- `landlord.datasource.auto-commit=false` (resources/application.properties:~87) + AdvisoryLockService.tryLock runs `SELECT pg_try_advisory_lock` through `landlordDataSource.getConnection()` and never commits. The pinned connection stays "idle in transaction" for the full per-tenant run (minutes for OrderRelease/StockSummary/Cleanup).
- If landlord PG has `idle_in_transaction_session_timeout` (or a PgBouncer/proxy idle-tx kill), the session is terminated mid-job: the advisory lock vanishes silently, a second replica acquires the same (job, tenant) lock and double-processes; unlock then hits a dead connection (only logged).
- UNVERIFIED: could not read the setting (MCP error). Check `SHOW idle_in_transaction_session_timeout` on landlord dev/uat/prd. Fix: set autoCommit(true) on the lock connection (conn.setAutoCommit(true) before the pin) so no tx is open.
- Callee bodies read: yes.

### F3 [MEDIUM, CONFIRMED by code, impact bounded] StockSummaryExportJob persists InventoryRecord chunks before OMS delivery - partial export leaves committed orphans and duplicates on retry
- `schedulejob/StockSummaryExportJob.java` exportStockSummary ~L443-600: inside `streamStockCount` (read-only tx, cursor) each chunk calls `inventoryRecordService.createEntitiesBulk` (REQUIRES_NEW, commits immediately, `service/InventoryRecordService.java:52`) and then enqueues to the OMS consumer thread. If the consumer fails/times out (consumerError, offer timeout), the stream aborts with earlier chunks already committed locally AND possibly some already sent; the tenant is marked failed. Next run snapshots again with fresh UUIDs (`record.setNumber(UUID.randomUUID())`), so the failed run's rows remain as a partial snapshot alongside the new full one.
- Failure scenario: OMS flaps mid-export on a large tenant -> inventory_record table holds partial AUTOMATIC snapshot at timestamp T; consumers of "latest snapshot" see an incomplete one if they pick by timestamp/type.
- Pattern is deliberate (SBDEV-2228 comments) but no cleanup/compensation of committed chunks. Callee bodies read: yes.

### F4 [LOW, CONFIRMED] TimezoneService caches the warehouse zone forever; invalidate methods have zero callers; a blank sysprop caches UTC permanently
- `service/TimezoneService.java:37,80-103,110-123`: `cache.computeIfAbsent(tenantKey, ...)` with no TTL. `invalidateCache`/`invalidateCacheAll` have no caller in src/main (grep). `parseToZoneId` returns UTC for null/blank/invalid and that UTC is cached.
- Scenario: tenant provisioned (or first job tick/request) before `System Time Zone` sysprop is set -> UTC cached; admin sets the real zone -> per-replica stale until restart; job registration (deriveSpecForCurrentTenant, e.g. `schedulejob/OrderReleaseJob.java:168`) and `todayInWarehouse()` (ReleaseOrderJobService:155, BillofladingService:779, OrderBatchCreationService:138/147) keep using UTC. Replicas that restarted at different times disagree.
- Known design per runbook 260523-UTC-TIMEZONE-MIGRATION ("operationally triggered via Actuator or restart") but no actuator/endpoint exists in code - NEW concrete gap. Fix: don't cache the UTC fallback; evict from SystemPropertyController save of that key (and bound with a TTL for cross-replica).

### F5 [LOW, CONFIRMED latent trap] `getWarehouseZoneId(String facilityCode)` keys the cache by the PARAM facility but reads the sysprop from the CONTEXT tenant DB
- `service/TimezoneService.java:62-78`. Javadoc says "reserved for callers that look up a facility other than the one in TenantContext", but the read goes through TenantContext's DB. All 6 current callers pass `current.getFacilityCode()` (OrderReleaseJob:168, ReplenishOrderJob:229, StockSummaryExportJob:192, EmptyPalletCleanupJob:119, CleanUpOldMessagesJob:161, StaleClubBatchCleanupJob:131), so benign today. A caller passing another facility would cache facility A's zone under facility B's key permanently (see F4).

### F6 [LOW, known/acknowledged] Tenant config caches are rebuilt with clear() then put() - not atomic
- `landlord/config/TenantConfigLoader.java:~88-108` (dbConfigCache.clear() then refill; authConfigCache.clear() then refill) while `TenantDbConfigCache`/`TenantAuthConfigCache` are plain ConcurrentHashMaps. Window is microseconds-ms every 5 min per replica: a concurrent pool build / JWT decoder / TenantHealthService / schedule reconcile can see an empty or partial map (SchedulingConfiguration.java:~1838 comment already acknowledges "snapshot taken during the tenant-cache refresh"). New concrete consequence not mentioned there: `refreshNow()` (provisioning, request thread) can interleave with `scheduledRefresh()`; `evictAbsentPools()` (TenantDynamicRoutingDataSource.java:665) then closes the live Hikari pool of an ACTIVE tenant whose entry is momentarily missing, aborting in-flight transactions. Needs two refreshes to overlap, so rare. Fix: build a new map and swap a volatile reference; serialize refresh.

### F7 [LOW, PLAUSIBLE] TenantPoolEvictor can close a pool under a long transaction that has not acquired a connection for >15 min
- `landlord/config/TenantPoolEvictor.java:30-40` evicts on `lastAccess` age (default 15 min); lastAccess is stamped only at connection acquisition (TenantDynamicRoutingDataSource.java:148,167). `removeTenant` -> `HikariDataSource.close()` aborts in-use connections. A single read-only stream/transaction (ReleaseOrderJobService.streamOrderPositionsForEach, WarehouseStockReportService.streamStockCount) that goes >15 min with no new acquisition (e.g. OrderRelease skipping thousands of already-released rows, or StockSummary blocked on OMS) is not protected. In practice the per-order/per-chunk REQUIRES_NEW calls re-stamp lastAccess, so exposure is the dead-air phases only. Fix: stamp on release too, or skip eviction while pool has active connections (`HikariPoolMXBean.getActiveConnections()>0`).

### F8 [LOW, CONFIRMED] Unbounded single-statement deletes in cleanup jobs (no batching, unlike CleanUpOldMessages)
- `repo/jpa/RestIdempotencyRepository.java:69-72` deleteOlderThan and `repo/jpa/OutboxMessageRepository.java:85-87` deleteSentOlderThan (called via `service/job/OutboxDispatchService.java:169`, REQUIRES_NEW) delete all expired rows in ONE statement per tenant per run, under the fleet-wide one-key lock (RestIdempotencyCleanupJob.java:105). After an outage/long retention growth this is a long tx with big WAL burst; and it holds the landlord lock-connection (F2) for the duration, delaying later tenants. Fix: LIMIT/ctid batches in a loop with per-batch REQUIRES_NEW, as MessageCleanupBatchService does.

### F9 [LOW, CONFIRMED] TenantHealthService clears the caller's TenantContext in finally
- `service/TenantHealthService.java:69,99` and `controller/TenantHealthController.java:75`: set/clear on a request thread where TenantFilter already set the context; the clear wipes the request's own context mid-request (harmless today because nothing after it needs tenant data, but any future post-processing in that request silently falls to landlord). Fix: restore previous value like TenantAwareTaskDecorator does.

### F10 [LOW, CONFIRMED] ThreadPoolTaskScheduler + dual-lock jobs: landlord pool arithmetic has little headroom
- `schedulejob/SchedulingConfiguration.java:264` (pool 15) vs landlord pool 10 (application.properties:82). Dual-lock jobs (CleanUpOldMessages, StockSummaryExport) pin 2 landlord connections per tenant while running; single-lock jobs pin 1; the two outbox lanes pin 1 each plus the findByActiveTrue read. Worst-case simultaneous: StockSummary 2 + CleanUp 2 + OrderRelease 1 + Replenish 1 + ReleaseExpired 1 + EmptyPallet 1 + StaleClub 1 + outbox x2 + pending-reversal 1 + rest-idempotency 1 = 13 > 10 (plus the read connection each). Pool starvation => tryLock logs "Failed to acquire" and returns false (silent skip) after the 20 s connection timeout; request paths that need landlord (health, provisioning) stall. Mitigated by cron staggering by tenant schedule; documented in properties comment for 10 jobs. Dual-lock removal (documented as TEMPORARY) would drop 4. PLAUSIBLE under coincident fires.

## Verified clean (read bodies)
- TenantFilter (landlord/config/TenantFilter.java): set, then try { chain } finally { clear }; public endpoints skip and never set; no async/ERROR dispatch (non-OncePerRequest filter => REQUEST only).
- Every tenant-iterating job sets context inside a per-tenant try and clears in finally, after which a catch/continue lets the next tenant run: OrderReleaseJob, ReplenishOrderJob, StockSummaryExportJob, CleanUpOldMessagesJob, ReleaseExpiredPickingOrdersFromUserJob, EmptyPalletCleanupJob (structure grep), StaleClubBatchCleanupJob (grep), RestIdempotencyCleanupJob, OutboxDispatcherJob, PendingReversalReconciliationJob, ClubRunJobPollerJob, SchedulingConfiguration (probe, bootstrap lambda, 6 group registrars, reconcile @Scheduled - each has finally clear; callerContext restored). Failure of one tenant does not abort the rest.
- Transaction opened after context set: all per-order/per-item work is REQUIRES_NEW on tenantTransactionManager (ReleaseOrderJobService, ReplenishOrderJobService x10 sites, MessageCleanupBatchService, OutboxDispatchService.cleanupSent, InventoryRecordService.createEntitiesBulk); orchestrators are deliberately non-transactional. The read-only outer streams (streamOrderPositionsForEach, streamStockCount) hold one connection+snapshot while REQUIRES_NEW work uses a second - documented SBDEV-2961/2228 pattern, writes never join the read-only tx.
- Cross-pod guards: all 9 business jobs + 2 outbox lanes + pending-reversal + idempotency cleanup take advisory locks (two-key per tenant or one-key fleet). Landlord connection used for the lock is the raw landlordDataSource (not the routing DS), so no tenant misroute of the lock. ThreadLocal pin slots are per-form, cleared in finally; tryLock failure paths close the conn. Math.toIntExact guarded before tryLock in runFor and runForCurrentTenant.
- Infrastructure @Scheduled (TenantConfigLoader.scheduledRefresh, TenantPoolEvictor, reconcileSchedules) are per-replica by design; reconcile is guarded by registrationLock (synchronized) which is JVM-local, correct because registrations are per-replica.
- ClubRunJobPollerJob / ClubRunExecutorConfig / ClubRunJobWorker: claim by DB lease (not in-memory), TenantAwareTaskDecorator + explicit set/restore in claimTask, SecurityContext rebuilt from job.requested_by on the pool thread, discard-on-saturation counted. Multi-pod safe via claim service.
- StockSummaryExportJob consumer thread: TenantAwareTaskDecorator captures tenant on the submitting thread, restores/clears in finally, bounded queue, bounded offer/POISON_PILL/join, daemon thread. Only note: SecurityContext is not propagated to that thread (sendList/createMessage run unauthenticated user) - cosmetic.
- ReplenishmentMaintenanceTrigger: afterCompletion hook re-sets tenant only when context empty, refuses on mismatched tenant, runs in REQUIRES_NEW TransactionTemplate (correct per Spring afterCompletion contract), failures swallowed with WARN (already documented in boundary map).
- KeycloakPasswordVerifier logout executor: HTTP-only, no DB/TenantContext use; bounded.
- No @Async/@EnableAsync, CompletableFuture, parallelStream (only a comment in CustomerorderBatchService:1544), no Quartz/ShedLock, no ReentrantLock. Only `synchronized`: SchedulingConfiguration.registrationLock (per-pod, correct) and SdrFunctionGuard lazy init (double-checked, fine).
- No TenantContext switch inside an open transaction found: setCurrentTenant occurs only in job loops, TenantHealthService, ReplenishmentMaintenanceTrigger (guarded), SchedulingConfiguration (no tx).
- Caches (sysprops/clients/locations/itemdata, Caffeine JwtDecoder/authority/user caches, KeycloakPasswordVerifier decoders) are keyed by TenantKeyBuilder tenant key (except TimezoneService, see F4/F5).
