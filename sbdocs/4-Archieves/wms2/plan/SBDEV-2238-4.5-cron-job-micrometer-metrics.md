# SBDEV-2238-4.5 — Micrometer Metrics for v2 Cron Jobs

**Ticket:** [SBDEV-2238](https://app.clickup.com/t/SBDEV-2238)
**Project:** wms2-api | **Version:** v2 | **Type:** improvement (observability)
**Priority:** Medium | **Severity:** LOW (no business-logic change; additive instrumentation only)
**Status:** draft (2026-05-18)
**Date:** 2026-05-18

> **Framing.** v2 wms2-api runs five scheduled jobs (`OrderReleaseJob`,
> `ReplenishOrderJob`, `StockSummaryExportJob`, `CleanUpOldMessagesJob`,
> `ReleaseExpiredPickingOrdersFromUserJob`). None of them today emit
> structured runtime metrics — no wall-time histogram, no success/failure
> counters, no last-run / last-success heartbeat gauges, no per-tenant
> breakdown. Ops cannot answer "did the replenishment job actually run on
> tenant X today" without scraping logs. This plan adds a uniform
> Micrometer instrumentation layer on top of the existing job bodies, with
> a shared `JobMetrics` helper class, plus enables the
> `/actuator/prometheus` scrape endpoint so Prometheus can consume the new
> metrics.
>
> Scope is deliberately additive. No business-logic change. No new
> `@Scheduled`, no new advisory lock, no transaction-boundary change. The
> existing `tryLock` / `unlock` skeleton is preserved exactly; metrics
> fire only on the lock-holder path.
>
> Out of scope: `StaleClubBatchCleanupJob`, `RestIdempotencyCleanupJob`,
> and `OutboxDispatcherJob` (documented as a parity gap in §11 — the
> first two predate this metrics convention; `OutboxDispatcherJob` already
> targets the `wms2.outbox.*` namespace per SBDEV-2221 and must not be
> instrumented under `wms2.cron.*` here).

## 1. Problem Statement

**Operational symptom (today, in v2).**
When a scheduled job fails for a single tenant, the only signal is a stack trace in `app.log` and a (possibly delayed) downstream complaint from a warehouse user ("we don't see new replenishments"). There is no way for ops to answer, without log-scraping:

- Did `OrderReleaseJob` run in the last 5 minutes? On all tenants?
- How long did `ReplenishOrderJob` take this hour?
- Which tenants saw a failure in `StockSummaryExportJob`, with what exception class?
- How often does `tryLock` fail (i.e. how often does a non-holder replica skip)?
- For `ReplenishOrderJob`, how many rows did each of the four sub-operations process per tenant?
- For `StockSummaryExportJob`, how often does the OMS consumer queue back-pressure produce a timeout?

There are no Prometheus metrics scraped today because `/actuator/prometheus` is not exposed; even if it were, the jobs do not emit anything beyond the legacy `stock_summary_export_aborted_total` counter buried in `WarehouseStockReportService`.

**Why this matters operationally.**

- A silent failure on one tenant for one job for one day can take 24 hours to surface as a user complaint.
- "Was the job actually scheduled" is a question ops cannot answer without log access.
- Capacity planning (e.g. "should `ReplenishOrderJob` be moved off the shared scheduler") requires wall-time histograms that do not exist.
- Alert rules (e.g. "page if no `OrderReleaseJob` success in the last 15 minutes") cannot be written.

## 2. Current Architecture

Each of the 5 in-scope jobs follows the same structural skeleton (paraphrased from `OrderReleaseJob.doCalculation`):

```java
void doCalculation() {
    if (!advisoryLockService.tryLock(JobLockId.ORDER_RELEASE)) return;
    try {
        for (TenantProfile tenant : tenants) {
            try {
                TenantContext.setTenant(tenant);
                if (!syspropService.getBooleanValue(ACTIVATION_KEY)) continue;
                // body — calls service, may throw
            } catch (Exception e) {
                LOG.error("Job failed for tenant {}: {}", tenant.getTenantName(), e.getMessage());
            } finally {
                TenantContext.clear();
            }
        }
    } finally {
        advisoryLockService.unlock(JobLockId.ORDER_RELEASE);
    }
}
```

Three observable variations:

1. **`ReplenishOrderJob`** adds a JVM-local guard:
   ```java
   private static final AtomicBoolean RUNNING = new AtomicBoolean(false);
   if (!RUNNING.compareAndSet(false, true)) return;
   try { ... } finally { RUNNING.set(false); }
   ```
   This is the same-JVM guard that runs *before* `tryLock`. A duplicate scheduler tick on the same pod is short-circuited without taking the advisory lock at all. The plan must distinguish "skipped because another replica holds the lock" from "skipped because this JVM is already running".
2. **`ReplenishOrderJob`** calls four sub-operations per tenant (`autoSplittingForFullPallet`, `singleSkuFullCaseShortageReplenishment`, `wholeFullCasePickingShortageReplenishment`, `partialBaseLastCaseShortageReplenishment`), each returning `List<Long>`. The plan emits a per-sub-op row counter.
3. **`StockSummaryExportJob`** writes to an in-memory `BlockingQueue` consumed by an OMS-facing thread; `omsQueue.offer(item, timeout, MILLISECONDS)` returning false is a back-pressure signal. The plan emits a consumer-timeout counter.

**Existing metric library state.** Micrometer is already on the classpath via Spring Boot's `spring-boot-starter-actuator`. `MeterRegistry` is auto-configured and injected into other services (e.g., `OmsNotificationService.wms2.oms.notification.failed`). What is missing is (a) the Prometheus registry implementation and (b) the exposure of the prometheus actuator endpoint.

## 3. Design / Proposed Fix

The plan introduces three artefacts: (a) a runtime dependency, (b) a config flag, (c) a shared helper class, then (d) wires every job through that helper.

### 3.1 Enable Prometheus scrape endpoint

**File:** `v2/wms2-api/pom.xml` — add runtime dependency:

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
    <scope>runtime</scope>
</dependency>
```

**File:** `v2/wms2-api/src/main/resources/application.properties` (~line 87) — change:

```
# Before:
management.endpoints.web.exposure.include=health,info,metrics,hikaricp
# After:
management.endpoints.web.exposure.include=health,info,metrics,hikaricp,prometheus
```

Why this is safe: `micrometer-registry-prometheus` is a passive registry. Adding it only changes what is scraped; no app behaviour changes. Adding `prometheus` to the exposure list opens `GET /actuator/prometheus` to whatever is already allowed to hit `/actuator/metrics` (Keycloak filter posture is unchanged).

### 3.2 Metric naming convention

Naming convention: `wms2.cron.<job>.<event>` matching the existing `wms2.oms.notification.failed` style.

| Metric | Type | Tags | Notes |
|---|---|---|---|
| `wms2.cron.<job>.duration` | Timer | — | Full `doCalculation` incl. all tenants |
| `wms2.cron.<job>.tenant_duration` | Timer | `tenant` | Per-tenant slice |
| `wms2.cron.<job>.rows_processed` | Counter | `tenant` | Job-specific count (rows emitted/processed) |
| `wms2.cron.<job>.success` | Counter | `tenant` | Tenant body completes without exception |
| `wms2.cron.<job>.failure` | Counter | `tenant`, `reason` | `reason` = exception simple class name |
| `wms2.cron.<job>.skipped_lock_busy` | Counter | — | `tryLock` returned false |
| `wms2.cron.<job>.skipped_not_activated` | Counter | `tenant` | Sysprop activation gate off |
| `wms2.cron.<job>.last_run_epoch_seconds` | Gauge | — | `AtomicLong`, updated every run |
| `wms2.cron.<job>.last_success_epoch_seconds` | Gauge | — | `AtomicLong`, updated only on clean run |

**Job-specific extras:**

- `ReplenishOrderJob`: `wms2.cron.replenish_order.suboperation_rows{tenant, sub_op}` — each sub-operation returns `List<Long>`; the counter records `list.size()`. `wms2.cron.replenish_order.skipped_jvm_busy` (no tags) — fires when the `RUNNING.compareAndSet(false,true)` returns false.
- `StockSummaryExportJob` has **two distinct timeout counters** — implementer must not collapse them:
  - `wms2.cron.stock_summary_export.consumer_timeout{tenant}` — fires at lines 210 and 227 when `omsQueue.offer(item, timeout, MILLISECONDS)` returns false during mid-stream batch streaming (back-pressure from the OMS consumer thread; the job continues processing).
  - `wms2.cron.stock_summary_export.shutdown_drain_timeout` (no `tenant` tag) — fires at line 237 when `omsQueue.offer(POISON_PILL, ...)` returns false, meaning the consumer was wedged and could not receive the shutdown sentinel at job completion. This is a distinct operational signal (consumer stuck at teardown, not during streaming) and must NOT be merged into `consumer_timeout`.

**Job-name segment mapping (snake_case to match Prometheus convention):**

| Class | metric segment |
|---|---|
| `OrderReleaseJob` | `order_release` |
| `ReplenishOrderJob` | `replenish_order` |
| `StockSummaryExportJob` | `stock_summary_export` |
| `CleanUpOldMessagesJob` | `clean_up_old_messages` |
| `ReleaseExpiredPickingOrdersFromUserJob` | `release_expired_picking` |

### 3.3 New helper class: `JobMetrics`

**New file:** `v2/wms2-api/src/main/java/net/aim_ai/wms/schedulejob/JobMetrics.java`

```java
package net.aim_ai.wms.schedulejob;

import io.micrometer.core.instrument.*;
import java.time.Instant;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicLong;

public final class JobMetrics {
    private final MeterRegistry registry;
    private final String jobSegment;
    private final AtomicLong lastRunEpoch = new AtomicLong(0);
    private final AtomicLong lastSuccessEpoch = new AtomicLong(0);

    public JobMetrics(MeterRegistry registry, String jobSegment) {
        this.registry = registry;
        this.jobSegment = jobSegment;
        Gauge.builder("wms2.cron." + jobSegment + ".last_run_epoch_seconds",
                      lastRunEpoch, AtomicLong::get).register(registry);
        Gauge.builder("wms2.cron." + jobSegment + ".last_success_epoch_seconds",
                      lastSuccessEpoch, AtomicLong::get).register(registry);
    }

    public void skippedLockBusy() {
        registry.counter("wms2.cron." + jobSegment + ".skipped_lock_busy").increment();
    }
    public void skippedJvmBusy() {
        registry.counter("wms2.cron." + jobSegment + ".skipped_jvm_busy").increment();
    }
    public void tenantSuccess(String tenant) {
        registry.counter("wms2.cron." + jobSegment + ".success", "tenant", tenant).increment();
    }
    public void tenantFailure(String tenant, String reason) {
        registry.counter("wms2.cron." + jobSegment + ".failure",
                         "tenant", tenant, "reason", reason).increment();
    }
    public void tenantSkippedNotActivated(String tenant) {
        registry.counter("wms2.cron." + jobSegment + ".skipped_not_activated",
                         "tenant", tenant).increment();
    }
    public void rowsProcessed(String tenant, long n) {
        registry.counter("wms2.cron." + jobSegment + ".rows_processed",
                         "tenant", tenant).increment(n);
    }
    public Timer.Sample startTenantTimer() {
        return Timer.start(registry);
    }
    public void stopTenantTimer(Timer.Sample s, String tenant) {
        s.stop(registry.timer("wms2.cron." + jobSegment + ".tenant_duration",
                              "tenant", tenant));
    }
    public void recordDuration(long nanos) {
        registry.timer("wms2.cron." + jobSegment + ".duration")
                .record(nanos, TimeUnit.NANOSECONDS);
    }
    public void markLastRun() {
        lastRunEpoch.set(Instant.now().getEpochSecond());
    }
    public void markLastSuccess() {
        lastSuccessEpoch.set(Instant.now().getEpochSecond());
    }

    // Job-specific extras
    public void replenishSubOpRows(String tenant, String subOp, long n) {
        registry.counter("wms2.cron." + jobSegment + ".suboperation_rows",
                         "tenant", tenant, "sub_op", subOp).increment(n);
    }
    // StockSummaryExportJob — back-pressure during mid-stream batch streaming (lines 210, 227)
    public void consumerTimeout(String tenant) {
        registry.counter("wms2.cron." + jobSegment + ".consumer_timeout",
                         "tenant", tenant).increment();
    }
    // StockSummaryExportJob — consumer wedged at shutdown; POISON_PILL offer failed (line 237)
    public void shutdownDrainTimeout() {
        registry.counter("wms2.cron." + jobSegment + ".shutdown_drain_timeout").increment();
    }
}
```

The helper is a plain `final class` (not a `@Component`) — each job constructs its own instance in its constructor, scoped to its own `jobSegment`. The gauges register once per instance, so each job emits exactly one `last_run` / `last_success` series.

### 3.4 Per-job wiring pattern

The pattern is identical across all 5 jobs. The `OrderReleaseJob` example:

```java
// BEFORE (paraphrased):
void doCalculation() {
    if (!advisoryLockService.tryLock(ORDER_RELEASE)) return;
    try {
        for (TenantProfile tenant : tenants) {
            try { /* body */ }
            catch (Exception e) { LOG.error(...); }
        }
    } finally {
        advisoryLockService.unlock(ORDER_RELEASE);
    }
}

// AFTER:
void doCalculation() {
    long startNs = System.nanoTime();
    if (!advisoryLockService.tryLock(ORDER_RELEASE)) {
        jobMetrics.skippedLockBusy();
        return;
    }
    try {
        for (TenantProfile tenant : tenants) {
            Timer.Sample tenantSample = jobMetrics.startTenantTimer();
            try {
                TenantContext.setTenant(tenant);
                if (!syspropService.getBooleanValue(ACTIVATION_KEY)) {
                    jobMetrics.tenantSkippedNotActivated(tenant.getTenantName());
                    continue;
                }
                long rowCount = /* body returns count */;
                jobMetrics.rowsProcessed(tenant.getTenantName(), rowCount);
                jobMetrics.tenantSuccess(tenant.getTenantName());
            } catch (Exception e) {
                jobMetrics.tenantFailure(tenant.getTenantName(),
                                         e.getClass().getSimpleName());
                LOG.error("Job failed for tenant {}: {}",
                          tenant.getTenantName(), e.getMessage());
            } finally {
                jobMetrics.stopTenantTimer(tenantSample, tenant.getTenantName());
                TenantContext.clear();
            }
        }
        jobMetrics.markLastSuccess();
    } finally {
        advisoryLockService.unlock(ORDER_RELEASE);
        jobMetrics.markLastRun();
        jobMetrics.recordDuration(System.nanoTime() - startNs);
    }
}
```

**Invariants preserved by the After block:**

- `tryLock` / `unlock` exact pairing — unchanged.
- `skippedLockBusy()` fires only when `tryLock` returns false (non-holder replicas).
- All other counters/timers fire **inside** the `tryLock` block — they cannot inflate by replica count.
- `markLastSuccess()` fires only if no uncaught exception escaped the outer for-loop (i.e. the `try` completed). Per-tenant failures are caught inside the inner try and recorded as `tenantFailure`, so they do not block `markLastSuccess`.
- `markLastRun()` fires in the outer `finally` — every time the lock holder enters the block, regardless of success or failure.
- `recordDuration` always fires for the lock holder; non-holders return early and do not contribute to the histogram.

**`ReplenishOrderJob` extras:**

```java
void doCalculation() {
    if (!RUNNING.compareAndSet(false, true)) {
        jobMetrics.skippedJvmBusy();
        return;
    }
    try {
        // ... same tryLock + tenant loop ...
        for (TenantProfile tenant : tenants) {
            // ...
            List<Long> autoSplit = replenishService.autoSplittingForFullPallet();
            jobMetrics.replenishSubOpRows(tenant.getTenantName(), "auto_split_full_pallet", autoSplit.size());
            List<Long> singleSku = replenishService.singleSkuFullCaseShortageReplenishment();
            jobMetrics.replenishSubOpRows(tenant.getTenantName(), "single_sku_full_case", singleSku.size());
            List<Long> wholeFull = replenishService.wholeFullCasePickingShortageReplenishment();
            jobMetrics.replenishSubOpRows(tenant.getTenantName(), "whole_full_case_picking", wholeFull.size());
            List<Long> partial = replenishService.partialBaseLastCaseShortageReplenishment();
            jobMetrics.replenishSubOpRows(tenant.getTenantName(), "partial_base_last_case", partial.size());
            // ...
        }
    } finally {
        RUNNING.set(false);
    }
}
```

**`StockSummaryExportJob` — tenant-name wiring inside `exportStockSummary()`:**

`exportStockSummary()` is a `private` helper called from inside the per-tenant loop (where `TenantContext` is already set). The `consumer_timeout` counter call inside this method requires the tenant name. The implementation MUST pass `tenantName` as a parameter — do NOT read `TenantContext.getCurrentTenant()` inside the helper, as it creates implicit coupling and the cron path already has the tenant available as a local variable.

Required signature change:
```java
// Before:
private void exportStockSummary(boolean isCronJob)

// After:
private void exportStockSummary(boolean isCronJob, String tenantName)
```

Pass `tenant.getTenantName()` from the call site (the per-tenant loop body). The `tenantName` parameter is then forwarded directly to `jobMetrics.consumerTimeout(tenantName)`.

**`StockSummaryExportJob` extras:**

The two offer sites have different operational semantics and must emit distinct counters:

```java
// Lines 210 and 227 — mid-stream batch offers (back-pressure during streaming):
if (!omsQueue.offer(item, TIMEOUT_MS, TimeUnit.MILLISECONDS)) {
    jobMetrics.consumerTimeout(tenant.getTenantName());   // wms2.cron.stock_summary_export.consumer_timeout{tenant}
    LOG.warn("OMS consumer queue offer timed out for tenant {}", tenant.getTenantName());
    continue;
}

// Line 237 — POISON_PILL sentinel offer (consumer wedged at shutdown):
if (!omsQueue.offer(POISON_PILL, TIMEOUT_MS, TimeUnit.MILLISECONDS)) {
    jobMetrics.shutdownDrainTimeout();   // wms2.cron.stock_summary_export.shutdown_drain_timeout (no tenant tag)
    LOG.error("OMS consumer did not drain after job completion — POISON_PILL offer timed out");
}
```

`shutdownDrainTimeout()` carries no `tenant` tag because the sentinel is sent once per job run (after the tenant loop completes), not per-tenant. This method must be added to `JobMetrics` alongside `consumerTimeout(String tenant)`.

## 8. Notes

### Scalability notes (operational)

- **Per-JVM gauges.** `last_run_epoch_seconds` and `last_success_epoch_seconds` are local to each replica. Across N replicas, you will see N series per job per gauge — only the holder updates on a given tick. Alert rules MUST aggregate: `max by (job)(wms2_cron_order_release_last_success_epoch_seconds)`.
- **`skipped_lock_busy` fires every tick on non-holders.** With N replicas and a 60s tick, expect roughly `(N-1) * 60 = 60(N-1)` increments per minute. This is the expected operational fingerprint of multi-replica deployment, not a bug.
- **All counters/timers fire inside the `tryLock` block** (other than `skipped_lock_busy` and `skipped_jvm_busy`). They cannot be inflated by replica count.
- **No new `@Scheduled`, cron expression, or advisory-lock ID** introduced. The 5 existing lock IDs (`100001..100005`) are unchanged.

### Alerting note — `app.cron=false` environments

`application.properties` defaults to `app.cron=false`. On these environments (non-production, local dev) the scheduled jobs never fire, so `last_run_epoch_seconds` and `last_success_epoch_seconds` gauges initialize to `0` in the `JobMetrics` constructor and stay at `0` indefinitely.

Alert rules must gate on `last_run_epoch_seconds > 0` to exclude never-run jobs:

```promql
# Correct — only fires if the job has run at least once AND is now stale:
(time() - wms2_cron_order_release_last_success_epoch_seconds > 900)
  and (wms2_cron_order_release_last_run_epoch_seconds > 0)

# Wrong — fires immediately on any app.cron=false environment (gauge stays at 0, time() - 0 is huge):
time() - wms2_cron_order_release_last_success_epoch_seconds > 900
```

This pattern applies to all 5 jobs. Without the guard, every staging / dev instance will permanently fire a stale-job alert from the moment the app starts.

### Follow-up work

- Grafana panels + alert rules (separate plan; depends on dashboards-as-code policy). All alert rules must incorporate the `last_run_epoch_seconds > 0` guard described above.
- Retrofit `StaleClubBatchCleanupJob`, `RestIdempotencyCleanupJob`, and `OutboxDispatcherJob` (parity gap — §11).
- Optionally migrate the legacy `stock_summary_export_aborted_total` counter in `WarehouseStockReportService` to the new `wms2.cron.stock_summary_export.aborted` prefix once the existing Grafana panels are confirmed (not in this plan).
