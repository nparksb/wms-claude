## 1. Problem Statement

**User-visible symptom (today, in v2).**
A Bill-of-Lading closed in WMS (`state=SHIPPED`) sometimes never reaches OMS, even though the truck has left the dock. Operators reconcile by hand the next morning. The only WMS-side trace is `Message(state=FAILED, processType=ORDER_BATCH_SHIPPED)` written by `OmsNotificationService.doSend()`, and that row is **not** keyed by `aggregate_id`, so it cannot be searched by BOL id and is not a replay queue.

**Three failure modes** in the current v2 code path (`BillofladingService.closeBOL` → `OmsNotificationService.sendAfterCommit` → `doSend()`):

1. **Pod crash between WMS tx commit and `afterCommit()` callback.** The BOL row is `SHIPPED` in the WMS DB, but the HTTP POST to OMS never fires. No row in any WMS table records the *intent* to notify, so there is nothing to retry from. Silent divergence.
2. **HTTP failure during POST.** `doSend()` writes one `Message(state=FAILED)` audit row and forgets. There is no scheduler that retries `FAILED` rows. Ops re-fire by hand.
3. **`messageService.createMessage` itself fails.** `doSend()`'s outer try only LOGs and increments a counter — no row is written at all, so even the audit trail is missing.

**Reproduction note (v2).**
On a dev tenant, set `app.oms.notification.timeout-ms=1` (or block the OMS host with iptables for the duration of the HTTP call), then call the close-BOL flow that targets `BillofladingService.closeBOL`. Observe: BOL transitions to `SHIPPED` in the WMS DB; a `Message(state=FAILED, processType=ORDER_BATCH_SHIPPED)` row appears (failure mode 2); no retry is ever attempted; OMS never receives the event. For failure mode 1, kill the pod with `kubectl delete pod --grace-period=0` immediately after the BOL state flip (inside the `afterCommit` window); the BOL is still `SHIPPED`, but no `Message` row exists. For failure mode 3, mock `messageService.createMessage` to throw — the BOL is still `SHIPPED`, no `Message` row appears, only a log line + metric.

## 2. Root Cause Analysis

### Bug 1 — `OmsNotificationService.doSend()` silently swallows OMS failure.

**Code reference:** `v2/wms2-api/src/main/java/net/aim_ai/wms/service/OmsNotificationService.java:97-118`.

```java
// OmsNotificationService.doSend (paraphrased)
try {
    response = httpRestService.post(urlPath, payload);     // (a) may throw
    messageState = response.is2xx() ? SENT : FAILED;       // (b)
    messageService.createMessage(messageState, ...);       // (c) may also throw
} catch (Exception e) {
    LOG.error("OMS notification failed: {}", e.getMessage());
    meterRegistry.counter("wms2.oms.notification_failed", ...).increment();
    // No row written. No retry. No idempotency.
}
```

Three concurrent root causes:

1. **No durable record of intent.** The HTTP POST is a *side-effect* of the WMS tx via `afterCommit`, not a row in a queue. Once the tx commits and the synchronization is dispatched, nothing in the DB says "WMS wants OMS to know about BOL #N." A pod crash between `commit()` and the synchronization's execution erases the intent. The `Message(FAILED)` audit row is only written **after** the POST attempt — a crash mid-POST produces no audit row at all.
2. **No retry mechanism.** Even on a clean 502/timeout, the failure is recorded once in `Message(state=FAILED)` and forgotten. There is no scheduler that scans `FAILED` rows.
3. **No idempotency on the wire.** OMS cannot tell "this is the same notification I already processed" from "this is a new one." A future replay layer added on top of the current code would risk double-shipping in OMS.

**v1 title clarification.** Historical SBDEV-2238 notes reference a v1 `BolClosedEventListener`. That listener does **not exist in v2**. In v2, the BOL ship notification is emitted inline from `BillofladingService.closeBOL:651-660` via `omsNotificationService.sendAfterCommit(...)`. This plan therefore rewrites the inline call site, not a listener. v1 carries its own fix track via the v1 plan family.

**Why `closeBOL` is the right first Phase-2 caller.**

- It is the **exact** call site the SBDEV-2221 pilot was designed to exercise. The integration tests, dispatcher tuning, and metric coverage in SBDEV-2221 already assume BOL as the canonical aggregate.
- It runs inside `@Transactional(tenantTransactionManager)` already — the enqueue participates automatically via the `MANDATORY` propagation on `OutboxService.enqueue` (SBDEV-2221 §3 Fix D).
- Payload is pre-serialized before the after-commit hook, so moving the serialization adjacent to the enqueue carries zero OSIV / lazy-loading risk.
- Volume is bounded (a handful of BOLs per hour per warehouse), so dispatcher pressure remains trivially below the SBDEV-2221 batch-size budget.

## 3. Architecture Overview

### Current (pre-fix) flow — best-effort audit log

```
closeBOL()  @Transactional(tenantTransactionManager)
   │
   ├── billofladingRepository.save(bol with state=SHIPPED)
   ├── payload = MAPPER.writeValueAsString(billOfLadingWebServiceDto)
   └── omsNotificationService.sendAfterCommit(url, payload, ORDER_BATCH_SHIPPED)
          │
          └── TransactionSynchronizationManager.registerSynchronization
                 │  (queued in JVM heap, NOT durable)
                 ▼
   ── tx commit ──
          │
          ▼
       afterCommit() fires
          │
          ▼
   doSend()  [OmsNotificationService:97-118]
          │
          ├── (a) HTTP POST to OMS                 ── failure mode 1: pod dies here
          ├── (b) compute SENT|FAILED              ── failure mode 2: 5xx ⇒ FAILED, no retry
          └── (c) messageService.createMessage(FAILED|SENT)
                   └── failure mode 3: createMessage throws ⇒ only LOG + counter
```

### Target (post-fix) flow — durable enqueue + dispatcher

```
closeBOL()  @Transactional(tenantTransactionManager)
   │
   ├── billofladingRepository.save(bol with state=SHIPPED)
   ├── payload = MAPPER.writeValueAsString(billOfLadingWebServiceDto)
   └── outboxService.enqueue(OutboxMessage.builder()
              .aggregateType("BILLOFLADING")
              .aggregateId(billOfLading.getId())
              .processType(ORDER_BATCH_SHIPPED)
              .destinationUrl(urlPath)
              .payload(payload)
              .idempotencyKey(UUID.randomUUID().toString())
              .build())
          │
          └── INSERT INTO outbox_message (...) status='PENDING'
              -- IN THE SAME WMS TX as the BOL save
   ── tx commit ──
          │
          ▼
   ── BOL = SHIPPED  AND  outbox_message row PENDING  ── atomic ──
          │
          ▼
   (separate pod / separate process) OutboxDispatcherJob (every 15s)
          ├── tryAdvisoryLock(JobLockId.OUTBOX_DISPATCHER)
          ├── for each tenant:  claim → POST(Idempotency-Key) → terminate
          └── retries on FAILED_RETRY with backoff; terminal alert on max-attempts
```

**Key invariant.** The BOL state and the outbox row are written in **one** WMS tx. They commit or roll back together. The HTTP POST happens **outside** any tx, on a separate scheduler thread, against a row whose existence proves intent.

## 4. Fix Design

The plan introduces exactly one fix.

### Fix A — Replace `sendAfterCommit(..., ORDER_BATCH_SHIPPED)` with `outboxService.enqueue(...)` in `closeBOL`.

**File:** `v2/wms2-api/src/main/java/net/aim_ai/wms/service/BillofladingService.java`, lines 651-660 + constructor.

**Problem.** As §2 explains, the current call chain (`closeBOL` → `sendAfterCommit` → `doSend`) is a fire-and-forget audit-log pattern with three concurrent failure modes (pod crash, HTTP failure with no retry, audit-write failure). The BOL state and the OMS notification are not atomic, the notification has no durable retry queue, and there is no idempotency key on the wire.

**Solution.** Write the OMS-notification **intent** as an `outbox_message` row in the same WMS tenant tx as the BOL save. The SBDEV-2221 dispatcher does the HTTP work asynchronously, with retries, idempotency-key headers, and terminal alerts. Atomicity, retryability, and idempotency are now properties of the DB row, not the JVM.

**Before** (`BillofladingService.java:651-660`):

```java
try {
    String urlPath = syspropService.getSysvalue(
        WmsConstants.SYSTEM_PROPERTY_WEBSERVICE_ORDER_BATCH_SHIPPED_URL_KEY);
    String payload = MAPPER.writeValueAsString(billOfLadingWebServiceDto);
    omsNotificationService.sendAfterCommit(urlPath, payload,
        WmsConstants.MessageProcessType.ORDER_BATCH_SHIPPED);
} catch (IOException e) {
    LOG.error("Failed to serialize BOL shipped payload for BOL={}: {}",
        billOfLading.getName(), e.getMessage());
}
```

**After:**

```java
try {
    String urlPath = syspropService.getSysvalue(
        WmsConstants.SYSTEM_PROPERTY_WEBSERVICE_ORDER_BATCH_SHIPPED_URL_KEY);
    String payload = MAPPER.writeValueAsString(billOfLadingWebServiceDto);
    OutboxMessage msg = OutboxMessage.builder()
        .aggregateType("BILLOFLADING")
        .aggregateId(billOfLading.getId())
        .processType(WmsConstants.MessageProcessType.ORDER_BATCH_SHIPPED)
        .destinationUrl(urlPath)
        .payload(payload)
        .idempotencyKey(UUID.randomUUID().toString())
        .build();
    outboxService.enqueue(msg);
} catch (IOException e) {
    LOG.error("Failed to serialize BOL shipped payload for BOL={}: {}",
        billOfLading.getName(), e.getMessage());
    meterRegistry.counter("wms2.outbox.serialize_failed",
        "aggregateType", "BILL_OF_LADING",
        "processType", WmsConstants.MessageProcessType.ORDER_BATCH_SHIPPED).increment();
}
```

**Constructor change.** Add `OutboxService outboxService` to the existing constructor parameter list, alongside the still-injected `OmsNotificationService` (the latter is retained until Phase-2 finishes — other code in the same service may still call it for non-BOL process types; this plan touches only the ORDER_BATCH_SHIPPED arm).

**IOException handling — intentional non-rethrow.** The `catch` block does **not** rethrow as a `BusinessException`. Mirrors SBDEV-2221 §3 Fix-A rationale: serialization failure for a BOL that has already met all business rules to be SHIPPED is an operator-driven recovery event, not a reason to roll back a closed BOL. The counter `wms2.outbox.serialize_failed` makes the failure observable; the BOL stays SHIPPED; ops use the metric panel to identify the orphaned BOL and re-emit by hand. Atomicity (outbox row + BOL state) is preserved on the **success path**; on the IOException path the BOL commits SHIPPED without an outbox row — this is intentional and bounded to a failure mode that has never been observed in production (Jackson serialization of a flat DTO).

**Why outbox, not alternatives?**

- **`@Retryable` on `doSend()`:** does not survive a pod crash; the queue is JVM-heap-resident.
- **A separate worker thread reading `Message(state=FAILED)` rows:** the `Message` table is keyed by an opaque audit id, not `(aggregate_type, aggregate_id)`, and is treated as audit log by the rest of the codebase — overloading it as a queue is the same antipattern that bit SBDEV-2214.
- **Kafka / RabbitMQ:** infrastructure investment that the v2 deployment topology does not currently support. The outbox table sits inside the per-tenant DB that already exists; no new infra.
- **Outbox (chosen):** durable in the same WMS tx, scheduler-polled, idempotency-keyed, already implemented by SBDEV-2221.
