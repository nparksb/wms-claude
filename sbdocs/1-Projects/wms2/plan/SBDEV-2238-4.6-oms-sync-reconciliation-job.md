# SBDEV-2238-4.6 — OMS Sync Reconciliation Job (Drift Detection Safety Net)

**Ticket:** [SBDEV-2238](https://app.clickup.com/t/SBDEV-2238)
**Project:** wms2-api | **Version:** v2 | **Type:** feature (Phase-2 closing safety net on top of the outbox pilot)
**Priority:** Medium | **Severity:** MEDIUM (silent OMS divergence today is bounded by manual ops review; this plan converts it into an alertable signal)
**Status:** draft (2026-05-18) — final reconciliation layer atop SBDEV-2221 outbox + the Phase-2 caller migrations (4.1..4.5).
**Date:** 2026-05-18

> **Framing.** The SBDEV-2238 family closes the WMS↔OMS notification-loss
> problem in three layers:
>
> 1. **SBDEV-2221** — durable outbox infrastructure (table, service, dispatcher,
>    advisory lock, metrics, idempotency keys). Wired to one pilot caller.
> 2. **SBDEV-2238-4.1..4.5** — each Phase-2 caller (BOL ship, order cancel,
>    order shipped, etc.) is migrated off `omsNotificationService.sendAfterCommit`
>    to `outboxService.enqueue`. Reliability of *delivery* is now bounded by the
>    dispatcher's retry policy.
> 3. **This plan (4.6)** — the *safety net*. The outbox guarantees the
>    notification *will eventually be delivered* if OMS comes back. But if OMS
>    is permanently down, or the outbox dispatcher exhausts retries (terminal
>    `FAILED_RETRY`), or a row never makes it into the outbox at all (e.g.
>    serialize-failed path in 4.1 §4 Fix A), WMS and OMS state diverge silently.
>    Today, divergence is caught only by user complaints. This plan converts
>    that into a daily, alertable Prometheus signal.
>
> Within scope: a new `@Scheduled` job `OmsSyncReconciliationJob` that compares
> WMS `customerorder` state against OMS state for orders mutated in the last
> N hours (default 24h, sysprop-configurable). On drift, it emits a counter
> with order-level ERROR logs — **no automatic remediation**. Surface-only.
>
> Out of scope: (a) any automatic re-emission of missing notifications — that
> belongs in a follow-up plan once the drift-rate baseline is known; (b) OMS-side
> changes — OMS must expose `GET /api/order/{externalId}` for the comparison,
> which must be confirmed by the OMS team before implementation begins; (c)
> full historical audit — only recently-mutated orders are checked, not the
> entire customerorder history.

## 1. Problem Statement

**User-visible symptom (today, in v2).**

When the WMS→OMS notification path fails to deliver (network blip during `afterCommit`, OMS down for an extended window, pod crash between commit and dispatch, terminal `FAILED_RETRY` on the outbox row, or the rare serialize-failed path in SBDEV-2238-4.1 §4 Fix A), WMS state advances (BOL closed, order shipped, order cancelled) but OMS may not know. Today the only signal is:

1. An ops engineer noticing a stuck order in OMS via dashboard.
2. A customer complaint propagating from the OMS-facing front-end.
3. Manual inspection of the `message` table on the WMS side (and/or the new `outbox_message` table once SBDEV-2221 lands).

There is no **automated, alertable** signal that WMS and OMS state have diverged. The outbox pattern (SBDEV-2221) tightens the *delivery guarantee*, but does not guarantee *eventual consistency* in the worst case where OMS is permanently unable to accept a particular event.

**Concrete divergence modes** the reconciliation job is designed to catch:

1. **OMS down for >24h.** Outbox dispatcher exhausts its retry budget; row sits in `FAILED_RETRY` with `attempts >= max_attempts`. WMS shows shipped; OMS shows in-flight.
2. **Outbox row never created.** SBDEV-2238-4.1 §4 Fix A documents an intentional non-rethrow on `IOException` during payload serialization — the BOL commits SHIPPED without an outbox row. Today there is zero signal.
3. **Pre-outbox legacy callers (not yet migrated).** Phases 4.2..4.5 progressively migrate the 16 non-BOL `sendAfterCommit` callers. Until all are migrated, the audit-log-only path can still drop notifications silently — and the operator has no way to know which orders are affected without a reconciliation pass.
4. **OMS acknowledges but loses state internally.** The dispatcher marks `dispatched_at` and `status=SENT` based on 2xx HTTP response, but a downstream OMS bug could still drop the event. (Low likelihood, but the reconciliation job catches it for free as a side benefit.)

**Why a reconciliation job is the right shape.**

- It is **read-only** on WMS state and **read-only** on OMS state — no double-writes, no remediation races.
- It is **rate-limited** by design (one scheduled run per day, windowed lookback) — bounded blast radius.
- It is **alertable** via a Prometheus counter — drift drives a pager, not a dashboard.
- It is **prerequisite-gated** by SBDEV-2221 — without a reliable outbox, the reconciliation would surface false positives from in-flight retries.

## 2. Job Design

### 2.1 WMS side — what to query (read-only)

Per tenant iteration, the job runs the following logical query (read-only, on the **tenant** transaction manager, `readOnly = true`):

```sql
SELECT co.id, co.external_id, co.state, co.updated_at
FROM customerorder co
WHERE co.updated_at >= NOW() - INTERVAL '<window_hours> hours'
  AND co.state IN ('SHIPPED', 'CANCELLED')
ORDER BY co.updated_at DESC
LIMIT 10000;   -- safety cap; cron-tuned via sysprop in a follow-up if needed
```

`<window_hours>` comes from `app.cron.oms_sync_reconciliation_window_hours` sysprop (int, default 24). The result set is the **candidate** set — orders WMS thinks have been notified to OMS.

For each candidate order, cross-check the `outbox_message` table:

```sql
SELECT om.id, om.status, om.dispatched_at, om.attempts
FROM outbox_message om
WHERE om.aggregate_type = 'CUSTOMERORDER'
  AND om.aggregate_id = :orderId
  AND om.process_type IN ('ORDER_BATCH_SHIPPED', 'ORDER_CANCELLED', ...)
ORDER BY om.created_at DESC
LIMIT 1;
```

Three branches:

- **No outbox row at all** → either the order pre-dates the outbox migration (Phase-2 not yet caught this caller), or the serialize-failed path in SBDEV-2238-4.1 §4 Fix A fired. Log WARN with order id; do **not** call OMS (no payload to compare against); increment `wms2.oms.sync.no_outbox_row{tenant}` counter. **Not** counted as drift.
- **Outbox row present, `dispatched_at IS NULL`** (still PENDING or in retry) → outbox dispatcher hasn't delivered yet. Log DEBUG; skip. **Not** counted as drift.
- **Outbox row present, `dispatched_at IS NOT NULL`, `status = 'SENT'`** → WMS believes OMS received the notification. Proceed to §2.2 OMS-side check.

### 2.2 OMS side — how to query (read-only HTTP GET)

For each order that passed the outbox-side check, issue:

```
GET {omsInstanceBaseUrl}/api/order/{externalId}
Headers:
  Authorization: Basic <OMS_API_USER>     (same as outbox dispatcher)
  x-tenant: <OMS_TENANT_ID>               (same as outbox dispatcher)
```

The OMS base URL is resolved from `syspropService.getOmsInstanceName()` (existing helper used by `OmsNotificationService` and other WMS→OMS surfaces — see `wms2-oms-integration-map.md` §2).

Three branches:

- **HTTP 200 with order body** → parse the OMS-side state. If `omsState` is consistent with `wmsState` (mapping table in §2.4), **no drift**. Log DEBUG; increment `wms2.oms.sync.orders_checked{tenant}` and `wms2.oms.sync.consistent{tenant}` counters.
- **HTTP 200 but `omsState` inconsistent with `wmsState`** (e.g. WMS=`SHIPPED`, OMS=`PROCESSING`), or **HTTP 404** (OMS does not know this order at all) → **drift detected**. Log at ERROR level with `orderId`, `externalId`, `wmsState`, `omsState`, `wmsUpdatedAt`. Increment `wms2.oms.sync.drift{tenant, processType=ORDER_STATUS_DRIFT}`.
- **HTTP timeout / 5xx / non-2xx other** → **NOT counted as drift** (OMS is unreachable, not authoritative right now). Log WARN. Increment `wms2.oms.sync.oms_unreachable{tenant}` counter. Move to next order — do not abort the whole tenant pass; OMS may be flaky for one order or one moment.

> **OMS endpoint prerequisite.** This depends on `GET /api/order/{externalId}` being available on the OMS side. It is listed as a hard prerequisite in §4.1 and the OMS team must confirm before implementation begins. If the endpoint is not available, this plan is blocked.

### 2.3 Advisory lock (cross-replica mutual exclusion)

`wms2-api` runs as multiple replicas. Without a lock, every replica would run the reconciliation in parallel, multiplying OMS GET load by N. The job follows the canonical pattern from `OrderReleaseJob.doCalculation`:

```java
public void doCalculation() {
    if (!advisoryLockService.tryLock(AdvisoryLockService.JobLockId.OMS_SYNC_RECONCILIATION)) {
        LOG.info("omsSyncReconciliationJob already running on another replica, skipping");
        jobMetrics.skippedLockBusy("OmsSyncReconciliationJob");
        return;
    }
    try {
        // ... per-tenant loop ...
    } finally {
        advisoryLockService.unlock(AdvisoryLockService.JobLockId.OMS_SYNC_RECONCILIATION);
    }
}
```

Uses lock ID **`100009L`** (next available after `OUTBOX_DISPATCHER = 100008L` per `AdvisoryLockService.JobLockId` block at `AdvisoryLockService.java:117-127`).

### 2.4 WMS → OMS state mapping (drift definition)

A drift verdict is only as good as the state mapping. The first implementation uses a conservative table; ambiguous mappings default to **no drift** (false negative preferred over false positive).

| WMS state | Acceptable OMS states | Drift if OMS reports... |
|---|---|---|
| `SHIPPED` | `SHIPPED`, `DELIVERED`, `COMPLETED` | anything else (incl. `IN_PROGRESS`, `PROCESSING`, `CANCELLED`) OR 404 |
| `CANCELLED` | `CANCELLED`, `REFUNDED` | anything else (incl. `SHIPPED`, `DELIVERED`) OR 404 |

The mapping table itself lives as a `private static final Map<String, Set<String>>` constant inside `OmsSyncReconciliationJob` so it can be updated in a single PR if OMS evolves. The OMS team must sign off on this table before implementation begins — recorded in §4.1 Prerequisites.

### 2.5 Sysprop gate

Controlled by a combination of two sysprops (matches the pattern of every other v2 cron job per `wms2-scheduled-jobs-catalog.md` §3):

- `app.cron=true` (global cron gate, lives in `application.properties`).
- `app.cron.oms_sync_reconciliation=true` (per-job activation sysprop per tenant; default OFF). Stored in `los_sysprop` per tenant.

If either is false → the per-tenant loop skips with `LOG.debug("omsSyncReconciliationJob not activated for tenant={}", ...)`. No metric is emitted for the skipped state — operators rollout per tenant, so debug-only is correct.

### 2.6 Window configuration

`app.cron.oms_sync_reconciliation_window_hours` sysprop (int, default 24). Stored in `los_sysprop` per tenant. Allows operators to narrow the window for noisy tenants or widen it during a known OMS-outage post-mortem without redeployment.

### 2.7 Schedule

`app.cron.oms_sync_reconciliation` cron string, default `0 0 2 * * *` (2 AM daily, off-peak). Stored as a property in `application.properties`, plumbed through `SchedulingConfiguration` (same wiring as every other business cron job).

## 3. Architecture Overview

### Current (pre-fix) state — no reconciliation

```
WMS                                           OMS
 │                                             │
 │  closeBOL / cancelOrder / etc.              │
 │  → (post-outbox migration) enqueue row      │
 │       outbox dispatcher → HTTP POST  ──────►│  (best-effort, retried on
 │                                             │   FAILED_RETRY)
 │                                             │
 │  *** no daily reconciliation pass ***       │
 │  *** divergence caught only by humans ***   │
```

### Target (post-fix) state — daily reconciliation safety net

```
WMS                                           OMS
 │                                             │
 │  closeBOL / cancelOrder / etc.              │
 │  → outbox row → dispatcher → HTTP POST ────►│
 │                                             │
 │  (daily, 2 AM, advisory-locked)             │
 │  OmsSyncReconciliationJob:                  │
 │    for each tenant:                         │
 │      query customerorder WHERE updated_at   │
 │         >= now() - 24h AND state IN (...)   │
 │      for each candidate order:              │
 │        check outbox_message dispatched      │
 │        if dispatched:                       │
 │          GET /api/order/{externalId}  ─────►│  (read-only)
 │          if state mismatch:                 │
 │            ERROR log + counter increment    │
 │                                             │
 │  Prometheus alert fires when                │
 │    rate(wms2.oms.sync.drift) > 0 over 1h    │
```

**Key invariants.**

- Read-only on both sides. No remediation happens here.
- Per-tenant lock release between OMS calls — no transaction held across HTTP egress.
- Advisory lock prevents N-replica amplification of OMS GET load.
- Sysprop gates allow per-tenant rollout independent of code deploy.

**Before:**

```java

public static final long CLEANUP_REST_IDEMPOTENCY = 100007L;
public static final long OUTBOX_DISPATCHER = 100008L;
```

**After:**

```java
public static final long STALE_CLUB_BATCH_CLEANUP = 100006L;
public static final long CLEANUP_REST_IDEMPOTENCY = 100007L;
public static final long OUTBOX_DISPATCHER = 100008L;
public static final long OMS_SYNC_RECONCILIATION = 100009L;
```

**Why 100009L.** Sequential allocation matches every prior addition (`OUTBOX_DISPATCHER` from SBDEV-2221 was 100008L). No gap, no reuse, no risk of colliding with a still-running old-version replica. `wms2-scheduled-jobs-catalog.md` §2 gets the matching row.

### Fix B — `OmsSyncReconciliationJob.java`

**File:** `v2/wms2-api/src/main/java/net/aim_ai/wms/schedulejob/OmsSyncReconciliationJob.java` — **NEW**.

**Shape** (paraphrased; full implementation lives in the executor's PR):

```java
@Service
public class OmsSyncReconciliationJob {
    private static final Logger LOG = LoggerFactory.getLogger(OmsSyncReconciliationJob.class);
    private static final int MAX_ORDERS_PER_TENANT = 10_000;
    private static final Map<String, Set<String>> WMS_TO_OMS_ACCEPTABLE_STATES = Map.of(
        "SHIPPED",   Set.of("SHIPPED", "DELIVERED", "COMPLETED"),
        "CANCELLED", Set.of("CANCELLED", "REFUNDED"));

    // dependencies (constructor-injected — see §5)
    private final AdvisoryLockService advisoryLockService;
    private final SyspropService syspropService;
    private final HttpRestService httpRestService;
    private final OutboxMessageRepository outboxMessageRepository;
    private final CustomerorderRepository customerorderRepository;
    private final TenantDbConfigurationRepository tenantDbConfigurationRepository;
    private final MeterRegistry meterRegistry;
    private final JobMetrics jobMetrics;
    private final ObjectMapper objectMapper;

    public void doCalculation() {
        if (!advisoryLockService.tryLock(AdvisoryLockService.JobLockId.OMS_SYNC_RECONCILIATION)) {
            LOG.info("omsSyncReconciliationJob already running on another replica, skipping");
            jobMetrics.skippedLockBusy("OmsSyncReconciliationJob");
            return;
        }
        Timer.Sample sample = jobMetrics.startTimer("OmsSyncReconciliationJob");
        try {
            List<TenantProfile> tenants = loadTenants();
            for (TenantProfile tp : tenants) {
                try {
                    TenantContext.setCurrentTenant(tp);
                    if (!isActivated()) {
                        LOG.debug("omsSyncReconciliationJob not activated for tenant={}/{}",
                            tp.getTenantName(), tp.getFacilityCode());
                        continue;
                    }
                    reconcileTenant(tp);
                } catch (Exception e) {
                    LOG.error("Reconciliation failed for tenant={}/{}",
                        tp.getTenantName(), tp.getFacilityCode(), e);
                    jobMetrics.failed("OmsSyncReconciliationJob", e.getClass().getSimpleName());
                } finally {
                    TenantContext.clear();
                }
            }
            jobMetrics.completed("OmsSyncReconciliationJob");
        } finally {
            jobMetrics.stopTimer(sample, "OmsSyncReconciliationJob");
            advisoryLockService.unlock(AdvisoryLockService.JobLockId.OMS_SYNC_RECONCILIATION);
        }
    }

    private void reconcileTenant(TenantProfile tp) {
        int windowHours = parseWindow();
        Date cutoff = Date.from(Instant.now().minus(windowHours, ChronoUnit.HOURS));
        List<String> targetStates = List.of("SHIPPED", "CANCELLED");

        Page<Customerorder> page = customerorderRepository.findByStateInAndUpdatedAtAfter(
            targetStates, cutoff, PageRequest.of(0, MAX_ORDERS_PER_TENANT));

        meterRegistry.counter("wms2.oms.sync.orders_checked",
            "tenant", tp.getTenantName()).increment(page.getNumberOfElements());

        for (Customerorder order : page) {
            checkOrder(tp, order);
        }
    }

    private void checkOrder(TenantProfile tp, Customerorder order) {
        OutboxMessage row = outboxMessageRepository
            .findTopByAggregateTypeAndAggregateIdAndProcessTypeInOrderByCreatedAtDesc(
                "CUSTOMERORDER", order.getId(),
                Set.of("ORDER_BATCH_SHIPPED", "ORDER_CANCELLED"))
            .orElse(null);
        if (row == null) {
            LOG.warn("No outbox row for orderId={} state={} — skipping OMS check",
                order.getId(), order.getState());
            meterRegistry.counter("wms2.oms.sync.no_outbox_row",
                "tenant", tp.getTenantName()).increment();
            return;
        }
        if (row.getDispatchedAt() == null) {
            LOG.debug("Outbox row for orderId={} not yet dispatched — skipping", order.getId());
            return;
        }
        try {
            String omsState = fetchOmsOrderState(order.getExternalId());
            if (!isConsistent(order.getState(), omsState)) {
                LOG.error("OMS sync DRIFT: orderId={} externalId={} wmsState={} omsState={} wmsUpdatedAt={}",
                    order.getId(), order.getExternalId(), order.getState(), omsState, order.getUpdatedAt());
                meterRegistry.counter("wms2.oms.sync.drift",
                    "tenant", tp.getTenantName(),
                    "processType", "ORDER_STATUS_DRIFT").increment();
            }
        } catch (OmsUnreachableException ue) {
            LOG.warn("OMS unreachable for orderId={} externalId={}: {}",
                order.getId(), order.getExternalId(), ue.getMessage());
            meterRegistry.counter("wms2.oms.sync.oms_unreachable",
                "tenant", tp.getTenantName()).increment();
        }
    }

    // ... fetchOmsOrderState(), isConsistent(), loadTenants(), parseWindow(), isActivated() ...
}
```

**Why each design choice:**

- **`reconcileTenant` is NOT `@Transactional`.** It opens a per-query read-only tx via Spring Data implicitly when the repository calls fire (Hibernate auto-flush off, `readOnly = true` on the repository finders themselves if needed). Long tx across HTTP egress is forbidden — see §9 row 4.
- **`OutboxMessage` finder is added to `OutboxMessageRepository`.** A derived JPA method, not native SQL, so no Testcontainers integration test is mandated for the finder itself.
- **`fetchOmsOrderState` throws a custom `OmsUnreachableException` on HTTP timeout / 5xx.** Distinguishes "OMS doesn't know the order" (404 → drift) from "OMS is unreachable right now" (5xx/timeout → not drift). The job's metric distinguishes the two — operators can tell whether their dashboard is showing real drift or a transient network blip.
- **Max 10,000 orders per tenant per run.** A safety cap. A tenant with 10k+ shipped/cancelled orders in 24h is a multi-week sales surge and operators will want to know separately; the job logs a WARN at the cap rather than continuing indefinitely.
- **`Map<String, Set<String>>` for state mapping** lives as a private static — single PR to evolve, no DB-driven config dance for a config that changes once a year.
