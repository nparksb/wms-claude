# SBDEV-3947 architect consult: a deterministic ORDER BY per export view
Code at origin/develop 219ad551. Views: `db/migration/V2.2.00__base_v2_schema.sql` (V2.2.00), no later V2.2.x redefines any of the six; onboarding `db/v1-to-v2-onboarding/schema/V1.2.04__utc_recreate_views.sql` (V1.2.04) has the same joins/GROUP BY/DISTINCT for all six (checked). Dev counts via q.sh, 2026-10-29. Every output column is text/varchar/numeric/bigint/int/timestamp(tz); **no json, no unorderable type** (information_schema check). NULLs order deterministically (ASC = NULLS LAST). Collations are the deterministic DB default, so text ties only on byte-equal strings. Each export chunk is its own HTTP request (`ReportService.java:79,171,205,243,284,319`), so the unstable `row_id` @Id cannot collide inside one Hibernate session.

## 1. receiving_dto_view: UNIQUE `(adviceid, advicepositionid)`
V2.2.00:4632-4678 `FROM advice a LEFT JOIN adviceposition ap ... GROUP BY a.id, ..., ap.id, ...`. All other joins go through PKs (`i.id = ap.itemdata_id`, `c.id = i.client_id`, `ult/bt/loc` by id), so a group is exactly one (a.id, ap.id). Advices with no positions give `ap.id NULL` once per advice. Dev: 42,550 rows, 42,550 distinct pairs, 133 null positions.
Cost: EXPLAIN ANALYZE `ORDER BY adviceid, advicepositionid OFFSET 40000 LIMIT 10000` = 5,057 ms against 5,038 ms unordered. The extra sort sits on top of the GroupAggregate and is noise. No index can help, since it sorts the aggregated output. The view's own `ORDER BY a.created DESC` still runs underneath and is wasted.

## 2. stock_view: UNIQUE `(item_id)`
V2.2.00:4685-4722 `FROM itemdata i LEFT JOIN stockunit su ... LEFT JOIN client c ON i.client_id = c.id ... GROUP BY i.id, i.item_nr, c.id, c.cl_nr`. `item_id = i.id` is the itemdata PK, and c is fixed by the FK. Dev: 8,805 rows, 8,805 distinct. Do NOT use `item_nr`: it is unique only per client (`UNIQUE (client_id, item_nr)`, V2.2.00:3580). Dev has 8,805 items and 8,718 distinct item_nr.

## 3. view_warehouse_location_report: UNIQUE `(sku_id, location_id)`
V2.2.00:2248-2267 `GROUP BY itemdata.id, ..., c.id, ..., loc.id, loc.name`, inner joins only. `sku_id = itemdata.id` and `location_id = loc.id`, both PKs, and c is fixed by itemdata's FK. Dev: 4,317 rows, 4,317 distinct. NB: the row-number column here is named `id`, not `row_id`, and `SELECT DISTINCT row_number()` is a no-op DISTINCT. To keep the view's current order (`ORDER BY c.cl_nr, itemdata.item_nr`) and still be total: `ORDER BY client_number, sku_number, location_id`. That works because `cl_nr` is UNIQUE (V2.2.00:3676) and `(client_id, item_nr)` is UNIQUE, so `(client_number, sku_number)` identifies the item.

## 4. flowbin_monitor_view: NO guaranteed unique set, so order by all output columns
V2.2.00:1124-1156 `GROUP BY loc.name, c.cl_nr, c.name, i.item_nr, i.name, su.amount, su.reservedamount, f.lowerbound, ..., f.*`. The output carries no PK. Groups are split by the raw `su.amount/su.reservedamount`, but the output is `round(...)`. So two stock units of one SKU in one flowbin, at 1.2 and 1.4, give two **fully identical** output rows. Identical rows are interchangeable, so a total order over all columns is still correct. Fan-out is otherwise bounded: `location.name` is UNIQUE (V2.2.00:3780), and `fix_location_assignment.assignedlocation_id` is UNIQUE (:3764), so `f.*` adds no fan-out. Dev: 2,068 rows, 2,068 distinct full rows, and `(location_name, sku_id)` is distinct on dev too, but that is data, not schema. Recommended: `ORDER BY location_name, client_id, sku_id, amount, reserved, requested_replenishment, client_name, sku_name, lower_bound, middle_bound, upper_bound, fix_assignment_exists, active`. `client_id` is needed because sku_id = item_nr is unique only per client. The leading location_name keeps the view's existing order.

## 5. order_detail_monitor_view: UNIQUE = all 15 output columns (the DISTINCT guarantees it)
V2.2.00:1642-1685 `FROM ( SELECT DISTINCT co.number ..., pop.pickfromstockunit_id ..., i.item_nr AS sku_id FROM customerorder co ... JOIN pickingorder_position pop ...) t1`. No PK reaches the output: `pop.id` and `cop.id` are dropped. DISTINCT removes identical rows (NULL treated as equal), so the 15 columns are unique by construction. Dev: 313 rows, 313 distinct full rows. The tempting subset `(picking_order_number, pick_from_stock_unit_id, sku_id)` gives only **151** distinct values out of 313, so it is NOT a key. `ORDER BY` all 15 non-row_id columns: `customer_order_number, picking_order_number, sku_id, pick_from_stock_unit_id, client_number, client_order_number, customer_external_number, tote_name, state, customer_order_fulfillment_type, location_name, priority, zone, parcel_external_number, carrier`.

## 6. parcel_monitor_view: `(customer_order_number, bol_number)` is total up to identical rows
V2.2.00:1834-1858: no GROUP BY or DISTINCT. `customerorder co` 1:1 via FK to si, ul (parcel), pallet, c, loc. Fan-out comes only from `LEFT JOIN billoflading_position bop ON bop.source_id = ul.id`, which has **no uniqueness** on source_id. Dev table: 1,804,622 bop rows, 414,227 distinct (source_id, billoflading_id), 411,910 distinct source_id. `co.number` is UNIQUE (V2.2.00:3620), and every other column is a function of (co, bo). So equal `(customer_order_number, bol_number)` means the rows are fully identical (duplicate bop rows on one BOL), and those are interchangeable. Dev view: 1,367 rows, 1,367 distinct pairs. To keep the view's existing order: `ORDER BY created DESC, customer_order_number, bol_number`.

## Q4: paged JPQL/HAL variants: same defect, separate fix, propose rather than fold in
The `Page<>` methods (`findByKeyword` on ReceivingDto/Stock/ViewWarehouseLocationReport/Parcel/OrderDetail, `findByKeywordAndClientName` on Flowbin, called from `ViewDtoService.java:1403,1437,1481-1485`) have no ORDER BY. The web UI adds `&sort=` only when a column is clicked (`wms2-web-ui/store/reports/receiving.js`, `inventory.js`, `skuLocation.js`: `(data.sortUrl ? '&sort=' + ... : '')`). So on-screen paging also skips or duplicates rows, and a user sort on a non-unique column (e.g. clientNumber) still ties. The fix belongs where the Pageable is built: append the per-view key above as a tiebreaker, `p.getSort().and(Sort.by(key))`, or set it on the SDR endpoint. It is not needed for the export fix. Interactive impact is lower. T1/T2 finding: put it on this ticket only if Nam wants scope added.

## Sibling sweep: the grep pattern under-counts
`LockOverviewDtoViewRepository.java:39-42` and `LockOverviewAllDtoViewRepository.java:46-49` use **positional** `OFFSET ?3 LIMIT ?4` with no ORDER BY, and `ReportService.java:128-129` pages them the same way. Grep `OFFSET :offset LIMIT :limit` misses both, so there are 8 affected queries, not 6. `StockrecordRepository.java:161,188` and `UnitloadRecordRepository.java:27` do order, but only by `created DESC`, which ties on equal timestamps. Add a PK tiebreaker (`, p.id`) if those views expose one (not checked).

## Trade-offs
- ASC by surrogate id (receiving, stock) is robust to inserts during a multi-chunk export: new rows land at the end. It changes the export's row order from the view's newest-first. Ordering DESC by id restores that UX, but then an insert mid-export shifts every later chunk by one row. Prefer ASC.
- ORDER BY does not give snapshot isolation. A row updated or deleted between chunks still shifts the offsets. Only keyset paging (`WHERE key > :last`) or a single streamed query fixes that. Out of scope for T2.
