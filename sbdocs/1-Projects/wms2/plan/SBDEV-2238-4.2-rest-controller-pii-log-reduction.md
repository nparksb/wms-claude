# SBDEV-2238-4.2 — REST Controller PII Log Reduction and Body Redaction

**Ticket:** [SBDEV-2238](https://app.clickup.com/t/SBDEV-2238)
**Project:** wms2-api | **Version:** v2 | **Type:** security / observability
**Priority:** Medium | **Severity:** MEDIUM-LOW (logging-only; no business-logic change)
**Status:** draft (2026-05-18)
**Date:** 2026-05-18

> **Framing.** Ticket SBDEV-2238 sub-item 4.2 reads: *"Full `orderBatchList`,
> `adviceList`, `skuList` are logged at INFO level. Payloads may include PII."*
>
> While drafting this plan we discovered the ticket's stated line numbers
> (`OrderRestController:94`, `AdviceRestController:111,323`, `SkuRestController:62`)
> are **constructor lines** in the current codebase — the ticket was written from
> a stale snapshot. The three named controllers already log only `.size()`, NOT
> the full payload. **The full-body logging missed by the ticket is in
> `FileImportController.java` at lines 304 and 386**, which call
> `LOG.info("create finished with {}", adviceList)` — logging the entire list
> via `toString()`. Note: line 304 (`importLocations`) logs `List<LocationUploadDto>`
> and line 386 (`importSkus`) logs `List<SkuUploadDto>` — neither contains PII fields.
> Both demotions are **observability-noise reductions**, not PII mitigations. The PII
> risk in this plan is addressed by Fix B (REST controllers potentially logging
> `OrderBatchDto`/`AdviceDto`/`SkuDto` payloads).
>
> Within scope: (A) demote the two `FileImportController` body-logging lines to
> DEBUG; (B) standardize the 14 INFO `.size()` call-sites in the three named
> controllers to a uniform `"size=N, ids=[a,b,c,d,e,...]"` summary via a new
> `RestPayloadLogSummary` utility; (C) surface the `Idempotency-Key` header in
> all log events for a request via an `IdempotencyFilter` MDC push.
>
> Out of scope: 16 `messageService.createMessage(objectMapper.writeValueAsString(...))` call
> sites across 3 controllers (`AdviceRestController:359,376,478,495,636,653`;
> `OrderRestController:351,502,519,593,610,725`; `SkuRestController:146,164,259,277`) persist
> full JSON bodies to the `message` table — that is a PII-at-rest concern and gets its own plan.

## 1. Problem Statement

**User-visible symptom (today, in v2).**
Production logs on busy days emit lines like:

```
INFO  ... create finished with [LocationUploadDto(locationName=A-01-01, areaName=RECEIVING, typeName=FLOOR, xPos=1, yPos=2, zPos=0, rackName=null, ...), ...]
INFO  ... create finished with [SkuUploadDto(sku=ABC-001, description=Widget A, ...), ...]
```

every time a file-import-driven location or SKU batch is processed. The full
list is materialized via `toString()` at INFO level — verbose, chatty, and
unnecessary for production monitoring even though neither `LocationUploadDto`
nor `SkuUploadDto` contains PII fields.

**Three classes of issue** across the REST surface:

1. **Observability noise reduction (medium priority).** `FileImportController` at line 304
   (`importLocations`) logs the entire `List<LocationUploadDto>` and at line 386
   (`importSkus`) logs the entire `List<SkuUploadDto>` via `toString()`. Neither
   DTO contains PII fields — `LocationUploadDto` is warehouse location metadata
   (`locationName`, `areaName`, `typeName`, `xPos`, `yPos`, `zPos`, `rackName`,
   `rackOrdinalNumber`, `rackRowName`, `rackRowOrdinalNumber`) and `SkuUploadDto`
   is SKU catalog metadata. The demotion is warranted on observability-noise grounds,
   not PII-mitigation grounds. The PII risk in this plan comes from REST controllers
   potentially logging `OrderBatchDto`/`AdviceDto`/`SkuDto` payloads (resolved by Fix B),
   not from `FileImportController`.
2. **Inconsistent observability (medium priority).** The 14 named-controller
   sites already log only `.size()`, but the format varies (`"create called with
   3"` vs `"create finished with 3"` vs `"delete finished"`) and includes no
   identifying keys. An operator triaging a failed `POST /api/v1/order` cannot
   tell which `batchId` was in the request without re-running the call.
3. **No request correlation (medium priority).** The `Idempotency-Key` HTTP
   header is consumed by `IdempotencyFilter` but never makes it into log events
   for the request. Operators cannot pivot from "OMS retried this request
   twice" to "which WMS log lines correspond to retry #2."

**Reproduction note (v2).**
On a dev tenant: `POST /api/v1/upload/locations` with a multi-element location list.
Tail `wms2-api.log`. Observe the `INFO ... create finished with [LocationUploadDto(...)]`
line containing the full DTO `toString()` output (verbose but no PII). For issue 2, `POST
/api/v1/order` with a 5-batch list: observe `INFO ... create called with 5` —
useful but missing `batchId` correlation. For issue 3, send any of the above
with `Idempotency-Key: abc-123` — `grep abc-123 wms2-api.log` returns zero
hits beyond `IdempotencyFilter`'s own start/end lines.

## 2. Root Cause Analysis

### Bug 1 — `FileImportController` logs full input lists at INFO via `toString()`.

**Code reference:** `v2/wms2-api/src/main/java/net/aim_ai/wms/controller/FileImportController.java:304` and `:386`.

```java
// FileImportController:304 — importLocations(): adviceList is List<LocationUploadDto> — no PII, observability noise
LOG.info("create finished with {}", adviceList);    // <-- LocationUploadDto list.toString() at INFO

// FileImportController:386 — importSkus(): adviceList is List<SkuUploadDto> — no PII, observability noise
LOG.info("create finished with {}", adviceList);    // <-- SkuUploadDto list.toString() at INFO
```

Both variables are misleadingly named `adviceList` in the source — the variable name reflects an
earlier version of the code when all import methods shared a parameter name. The types are different:
line 304 = `List<LocationUploadDto>`, line 386 = `List<SkuUploadDto>`.

slf4j's `{}` placeholder calls `List.toString()`, which iterates and calls each element's
`toString()`. Neither `LocationUploadDto` (fields: `locationName`, `areaName`, `typeName`, `xPos`,
`yPos`, `zPos`, `rackName`, `rackOrdinalNumber`, `rackRowName`, `rackRowOrdinalNumber`) nor
`SkuUploadDto` contains PII fields. This is an **observability-noise reduction**, not a PII
mitigation. The PII risk in this plan comes from the REST controllers potentially logging
`OrderBatchDto`/`AdviceDto`/`SkuDto` payloads (resolved by Fix B), not from `FileImportController`.

The default log level for `net.aim_ai` is `DEBUG` in
`application.properties:8`. There is no `application-prod.properties` in
`src/main/resources/` — production must override this externally (K8s ConfigMap,
Spring Cloud Config, or JVM `-D` flag). If production has not applied such an
override, the level remains DEBUG in all environments. Either way, the
`LOG.info(...)` call is at INFO — it survives any DEBUG-suppressing override and
shows up in the prod log aggregator.

### Bug 2 — INFO summaries across the three named controllers have inconsistent format and lack identifying keys.

**Code references:** `OrderRestController.java` (7 sites), `AdviceRestController.java` (2 sites), `SkuRestController.java` (5+ sites). Lines tabulated in §0.

All 14 sites already log only `.size()` — there is no PII leak today in the
named controllers. However:

- Format varies: `"create called with {}"`, `"updatePriority finished with {}"`,
  `"delete finished"`. Some include the verb, some include the verb + phase
  (called/finished), some omit the size entirely.
- No top-level identifying field is logged. For `orderBatchList`, the
  `batchId`s are stable, ops-meaningful keys but never make it into the log.

The fix is structural, not security-driven: standardize the format and surface
the top-level IDs so an operator can correlate a log line to a specific batch
without re-running the request.

### Bug 3 — `IdempotencyFilter` extracts the `Idempotency-Key` but never pushes it to MDC.

**Code reference:** `v2/wms2-api/src/main/java/net/aim_ai/wms/landlord/config/IdempotencyFilter.java`.

The filter parses the `Idempotency-Key` header, checks for an existing cache
entry, and short-circuits or proceeds — but it never calls `MDC.put(...)`. The
logback pattern in `logback-spring.xml` therefore cannot include the key, and
log events for the request do not carry the correlation identifier.

This is observability debt, not a security defect; bundling it into the same
PII-reduction PR is justified because the same set of reviewers and the same
test surface (controller-test harness + filter unit test) cover both. The
follow-up plan that handles request-body redaction at the filter layer will
inherit the MDC infrastructure that this plan establishes.

## 3. Architecture Overview

### Current (pre-fix) flow

```
HTTP request
   │
   ▼
IdempotencyFilter.doFilterInternal()
   ├── String key = req.getHeader("Idempotency-Key");
   ├── if (cache.contains(key)) → short-circuit (replay cached response)
   └── chain.doFilter(req, resp)
           │
           ▼
       OrderRestController.create(orderBatchList)
           ├── LOG.info("create called with {}", orderBatchList.size())   <-- size only, but inconsistent format
           ├── ... business logic ...
           └── LOG.info("create finished with {}", orderBatchList.size())

       FileImportController.createAdviceList(adviceList)
           ├── LOG.info("import inbound advice called with {}", adviceList.size())   <-- safe
           ├── ... business logic ...
           └── LOG.info("create finished with {}", adviceList)             <-- LEAK: full list toString()
```

### Target (post-fix) flow

```
HTTP request
   │
   ▼
IdempotencyFilter.doFilterInternal()
   ├── String key = req.getHeader("Idempotency-Key");
   ├── MDC.put("idempotencyKey", key);                                     <-- NEW (Fix C)
   ├── if (cache.contains(key)) → short-circuit
   ├── try {
   │     chain.doFilter(req, resp);
   │  } finally {
   │     MDC.remove("idempotencyKey");                                     <-- NEW (Fix C) — leak-safe
   │  }
           │
           ▼
       OrderRestController.create(orderBatchList)
           ├── LOG.info("create called: {}",
           │        RestPayloadLogSummary.of(orderBatchList, OrderBatchDto::getBatchId))   <-- NEW (Fix B)
           │   → "create called: size=5, ids=[B1,B2,B3,B4,B5]"
           ├── ... business logic ...
           └── LOG.info("create finished: {}",
                    RestPayloadLogSummary.of(orderBatchList, OrderBatchDto::getBatchId))

       FileImportController.createAdviceList(adviceList)
           ├── LOG.info("import inbound advice called with {}", adviceList.size())   (unchanged-safe)
           ├── ... business logic ...
           └── LOG.debug("create finished with {}", adviceList)             <-- DEMOTED (Fix A)
```

**Key invariants.**

1. INFO never carries a full DTO `toString()` payload. Only `size=N, ids=[...]`
   (top-level IDs) or `size` alone.
2. MDC is push-pop symmetric — every `put` is paired with a `remove` in a
   `finally`, so the key cannot leak to the next request on a re-used thread.
3. No controller signature changes — `RestPayloadLogSummary` is invoked at the
   call site only; existing tests that don't inspect logs continue to compile
   and pass unmodified.

## 4. Fix Design

### Fix A — Demote `FileImportController` body-logging lines to DEBUG.

**File:** `v2/wms2-api/src/main/java/net/aim_ai/wms/controller/FileImportController.java`, lines 304 and 386.

**Problem.** As §2 Bug 1 explains, these two lines log the full input list via `toString()` at INFO,
creating chatty, verbose production logs regardless of PII content. Fix A addresses
**observability noise**, not a PII mitigation — neither `LocationUploadDto` nor `SkuUploadDto`
contains PII fields.

**Solution.** Change `LOG.info(...)` to `LOG.debug(...)`. Two-line change, no
new utility needed for this fix. The lines remain useful for local debugging but
no longer reach prod log aggregation when prod is at INFO.

**Before:**

```java
// FileImportController.java:304 — importLocations(): adviceList is List<LocationUploadDto> — no PII, observability noise
LOG.info("create finished with {}", adviceList);

// FileImportController.java:386 — importSkus(): adviceList is List<SkuUploadDto> — no PII, observability noise
LOG.info("create finished with {}", adviceList);
```

**After:**

```java
LOG.debug("create finished with {}", adviceList);  // line 304
LOG.debug("create finished with {}", adviceList);  // line 386
```

**Variable name note.** Both variables are misleadingly named `adviceList` in the source — the
name reflects an earlier version of the code when all import methods shared a parameter name.
The types are different: line 304 = `List<LocationUploadDto>` (inside `importLocations()`),
line 386 = `List<SkuUploadDto>` (inside `importSkus()`). The demotion to `LOG.debug` applies
the same way regardless of type.

**Why not delete the lines outright?** They are the only diagnostic an operator
has when reproducing a file-import bug locally. Keeping them at DEBUG preserves
that path while removing the production noise. Production log level for
`net.aim_ai` must be overridden externally to INFO (K8s ConfigMap, Spring Cloud
Config, or JVM `-D` flag) — `application-prod.properties` does not exist in
`src/main/resources/`. Confirm this override is in place during the
implementation prerequisite check (§6.1 row 3).

**Test naming.** The test for line 304 should be named
`importLocations_doesNotLogFullListAtInfo` and the test for line 386 should be named
`importSkus_doesNotLogFullListAtInfo` — distinct test methods for distinct endpoints.

### Fix B — Introduce `RestPayloadLogSummary` utility; apply to 14 INFO call-sites.

**New file:** `v2/wms2-api/src/main/java/net/aim_ai/wms/util/RestPayloadLogSummary.java`.

**Problem.** The 14 INFO sites in the three named controllers vary in format,
log only `.size()`, and omit identifying keys (`batchId`, `referenceId`,
`sku` — the SKU catalog code, field name in `SkuDto.java`).

**Solution.** A small utility that takes a `List<? extends Object>` and a
`Function<T, String>` extractor and produces `"size=N, ids=[a,b,c,d,e,...]"`
(max 5 IDs, ellipsis after if N > 5). Null-safe on both the list and individual
IDs.

**Signature:**

```java
public final class RestPayloadLogSummary {
    private static final int MAX_IDS = 5;

    private RestPayloadLogSummary() {}

    /**
     * Produce a PII-safe summary of a REST request payload list.
     * @return "size=N, ids=[id1,id2,...]" — never logs full DTO body.
     */
    public static <T> String of(List<T> items, Function<T, String> idExtractor) {
        if (items == null) {
            return "size=0";
        }
        int size = items.size();
        StringBuilder ids = new StringBuilder("[");
        int shown = 0;
        for (T item : items) {
            if (shown >= MAX_IDS) { ids.append("..."); break; }
            String id = item == null ? null : idExtractor.apply(item);
            if (id == null) continue;
            if (shown > 0) ids.append(',');
            ids.append(id);
            shown++;
        }
        ids.append(']');
        return "size=" + size + ", ids=" + ids;
    }
}
```

**Application examples:**

```java
// OrderRestController.java:121
LOG.info("create called: {}",
    RestPayloadLogSummary.of(orderBatchList, OrderBatchDto::getBatchId));

// AdviceRestController.java:128
LOG.info("create called: {}",
    RestPayloadLogSummary.of(adviceList, AdviceDto::getReferenceId));

// SkuRestController.java:79
LOG.info("create called: {}",
    RestPayloadLogSummary.of(skuList, SkuDto::getSku));
```

**ID extractor choice.** Use the natural top-level identifier on each DTO:

| DTO | Extractor | Rationale |
|---|---|---|
| `OrderBatchDto` | `OrderBatchDto::getBatchId` | Stable, ops-meaningful, no PII. |
| `AdviceDto` | `AdviceDto::getReferenceId` | Stable, ops-meaningful, no PII. |
| `SkuDto` | `SkuDto::getSku` | Catalog code, no PII. Field is named `sku` (not `skuCode`) in `SkuDto.java:7`. Getter verified as `getSku()` at line 33. |

These getters are verified to exist on each DTO during the verify-script's
positive checks.

> **Getter verification note (REQUIRED change 1):** `SkuDto` does NOT have a `getSkuCode()` method.
> The field is named `sku` (see `SkuDto.java:7`) and the getter is `getSku()` (see `SkuDto.java:33`).
> Any reference to `SkuDto::getSkuCode` in this plan or its implementation is incorrect and must use
> `SkuDto::getSku` instead.

**Format choice (`"size=N, ids=[a,b,c,d,e,...]"`).** Single line, key=value
shape that grep / `jq` / Splunk field-extractors can parse without a custom
pattern. The trailing `...` after 5 IDs bounds the line length even for
1000-item batches.

### Fix C — `IdempotencyFilter` MDC push + logback pattern update.

**Files:**

- `v2/wms2-api/src/main/java/net/aim_ai/wms/landlord/config/IdempotencyFilter.java` — `doFilterInternal` body.
- `v2/wms2-api/src/main/resources/logback-spring.xml` — pattern layout.

**Problem.** The `Idempotency-Key` header is consumed but never surfaces in
log events. Operators cannot correlate retries to log lines.

**Solution.** Push the key into MDC after extraction; remove it in a `finally`
block; expand the logback pattern to include `%X{idempotencyKey:-}` (empty
string default when the key is absent).

**Before** (sketch — actual filter has more logic):

```java
@Override
protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp, FilterChain chain)
        throws ServletException, IOException {
    String key = req.getHeader("Idempotency-Key");
    // ... existing dedup logic ...
    chain.doFilter(req, resp);
}
```

**After (correct placement — verified against actual `doFilterInternal` structure):**

```java
// AFTER (correct placement):
@Override
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
        throws ServletException, IOException {

    // ... unauthenticated check (lines ~95-101) — NOT in the MDC scope
    // ... missing/blank key check (lines ~104-107) — NOT in the MDC scope
    // ... regex validation (lines ~113-115) — NOT in the MDC scope

    // After regex validation passes — safe to push validated key into MDC
    MDC.put("idempotencyKey", key);
    try {
        // ... CONFLICT/REPLAYED/IN_FLIGHT checks (lines ~118-165) — early returns still covered by finally
        // ... inner try/finally for chain.doFilter + persistResponse (existing code, stays nested inside)
    } finally {
        MDC.remove("idempotencyKey");
    }
    // Unauthenticated and missing-header paths never reach here — no MDC key was pushed — correct
}
```

**MDC placement rationale — all 5 early-return paths in `doFilterInternal`:**

The actual `doFilterInternal` (verified against `IdempotencyFilter.java:90-188`) has 5 early-return
paths before `chain.doFilter` runs. The MDC push must be placed correctly relative to each:

| Path | Line approx. | Has a valid `key`? | MDC pushed? | Reason |
|---|---|---|---|---|
| Unauthenticated → `return` (line ~100) | ~96-101 | No (before header read) | No | Guard is before `key = request.getHeader(...)` — MDC push must be AFTER regex validation |
| Missing/blank `Idempotency-Key` → `chain.doFilter(); return;` (line ~104-107) | ~104-108 | No (null/blank) | No | Key is invalid — do not push |
| Invalid key regex → `return` (line ~115) | ~109-116 | Syntactically invalid | No | Regex validation FAILS — do not push |
| `ClaimResult.CONFLICT` → `return` (line ~132) | ~126-133 | Yes (validated key) | Yes — outer `finally` covers this | Key is valid, request rejected; MDC is still useful for log correlation; `finally` cleans up |
| `ClaimResult.REPLAYED` → `return` (line ~151) | ~135-152 | Yes (validated key) | Yes — outer `finally` covers this | Replay path; key is valid; `finally` cleans up |
| `ClaimResult.IN_FLIGHT` → `return` (line ~162) | ~154-162 | Yes (validated key) | Yes — outer `finally` covers this | In-progress rejection; key is valid; `finally` cleans up |

**Critical placement rules:**

- "MDC push occurs AFTER the regex validation succeeds (post-line ~115) — invalid keys are never pushed."
- "MDC is NOT pushed on: unauthenticated requests, missing/blank `Idempotency-Key` header."
- "MDC IS pushed (and cleaned up) on: CONFLICT, REPLAYED, IN_FLIGHT early returns — the outer `finally` covers all paths from the push point."
- "The existing inner `try/finally` (lines ~167-187) for `persistResponse` stays nested inside the outer `try` block — two nested finally blocks, both correct."

**`logback-spring.xml`** — append `%X{idempotencyKey:-}` to the existing
encoder pattern (a single-token append; the `:-` syntax expands to an empty
string when the MDC key is absent so log lines from non-filtered paths remain
clean).

**Leak risk.** `MDC` is `ThreadLocal`-backed. Tomcat re-uses request threads, so
a missed `remove` would carry the previous request's key into the next event on
the same thread. The unit test `idempotencyFilter_twoSequentialRequests_mdcClean`
proves the `finally` block clears MDC between requests.
