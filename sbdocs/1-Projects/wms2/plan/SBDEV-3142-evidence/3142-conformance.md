## 10. The deliberate §3.6 `GUARDED` deferral — **reverting was CORRECT**

Scored as instructed: assessed, not marked MISSING. Verified `FunctionGuardInterceptor.GUARDED` does
**not** contain `ReportController` (`FunctionGuardInterceptor.java:112`, 14 entries, unchanged).

The escalation is well-founded, and the contradiction is structural rather than a matter of taste:

1. `UserControllerPublicHandlerUnitTest` **AC-4d** asserts a three-way equality —
   `GOLDEN_MAP.keySet() == EXPECTED_GUARDED == production GUARDED`, by simple name.
2. `GOLDEN_MAP` is `Map<String controllerSimpleName, String ONE function>`
   (`FunctionGuardArchTest.java:70`).
3. `FunctionGuardArchTest` **AC-1** requires every `GOLDEN_MAP` key to carry a **class-level**
   `@RequiresFunction` (`functionsOn(Class)`, `:230`), and **AC-2** requires that class-level set to
   equal exactly the one mapped function (`:248-251`).

So enrolling `ReportController` in `GUARDED` forces a `GOLDEN_MAP` entry, which forces a **class-level**
`@RequiresFunction` with **exactly one** function — precisely what §3.2 forbids, and what my M4 mutant
shows 403s two mobile screens. The two requirements are directly contradictory; there is no version of
this change that satisfies both without restructuring another ticket's ratchet.

Worth stating for whoever picks up the escalation: the blocker is **entirely the test model**, not a
production risk. §3.6's runtime argument holds — `FunctionGuardStartupAssertion:148-149` keys on
`declaringClass`, so `DashboardController`'s own handlers are skipped and cannot become boot
violations. The real fix is to generalise `GOLDEN_MAP` to admit a guarded class whose gating is
method-level-only, which is genuinely a separate piece of work. Reverting and escalating was the right
call.
