## (c) Is the root cause fully explained?
What is solid: at 54be5a40~1, sendStockUnitToNirvana called this.changeAmount (self-invocation, so changeAmount's own @Transactional never applied) and changeAmount does a lock read. Via LockReads.forUpdate (SBDEV-3286, 2026-10-09, commit 0bab9af6) that is entityManager.unwrap(SessionImplementor) with no tx -> IllegalStateException "No transactional EntityManager available", which neither catch block handles -> 500. The fix (a tx on the service entry points) is correct for this mechanism and the IT would have failed before it.
What is NOT explained, and I could ground part of it:
1. The IllegalStateException mechanism DID NOT EXIST on PRD in September. LockReads.forUpdate was introduced in changeAmount by 0bab9af6 on 2026-10-09; the PRD deletes stopped 2026-09-11. So the "No transactional EntityManager" mechanism cannot be what stopped them on Sept 11. Before Oct 9 (e.g. at 1d5c8bef, Sept 10) changeAmount called stockunitRepository.findByIdForUpdate (a @Lock(PESSIMISTIC_WRITE) @Query method on an interface with no @Transactional) followed by entityManager.refresh(stockUnit). If the IT failed at 1d5c8bef it failed on that call or the refresh (a different exception than today's). Ask whoever saw that failure for the exception class.
2. Between tags v0.0.24 (2026-09-09) and v0.0.26 (2026-09-15) I diffed StockunitBusinessService, UnitloadService, UnitLoadController, StockunitRepository (only an unrelated projection was added) and the pom/application.properties: nothing in the delete call path changed on Sept 11, and spring-boot-starter-parent stayed 3.5.9 (no Hibernate bump). 7316ddb5 (2026-03-28) is an ancestor of v0.0.21 and later. So a code diff does not explain Sept 11.
3. Most likely explanation I can offer, labelled UNGROUNDED: a runtime/environment difference, not a code diff. A pessimistic-lock query run with NO transaction can succeed under autocommit on PostgreSQL (SELECT ... FOR UPDATE just locks for one statement) in some Hibernate/Spring paths, while the IT, which runs with class-level NOT_SUPPORTED under a different EntityManager setup, throws. If that holds, the 64 PRD deletes ran through a non-tx path that worked until something else changed. Candidates to check, in order of cheapness: (i) the image/tag PRD actually ran before and after Sept 11 15:33 UTC (actuator/info build.time, per memory note on deployed-vs-HEAD) and whether it was an older image that predates 7316ddb5's inclusion; (ii) the first PRD log occurrence of TransactionRequiredException / "No transactional EntityManager" / InvalidDataAccessApiUsageException with its timestamp and class; (iii) whether the 64 earlier deletes came through /deleteContainer at all (stockrecord activitycode MANUAL_REMOVAL joined to user/endpoint timing) or through a path that already had a tx. I could not do (ii)/(iii): the tenant DB MCP servers failed to connect and I was told no DB.
Risk if left open: the fix is correct for the failure the IT reproduces, but the PRD regression date is not explained by it. If PRD actually broke on Sept 11 for a different reason, this PR may fix a real defect without fixing THE defect. AC-9 (PRD recheck) is the safety net; I recommend not closing the ticket on merge alone.
