## 1. Problem Statement

The WMS `OmsSyncReconciliationJob` (SBDEV-2238-4.6) compares WMS `customerorder` state against OMS state for
recently-mutated orders and emits an alertable drift counter. It needs a **read-only** OMS endpoint that returns
the current order state for a given WMS external id. No such endpoint is confirmed to exist on OMS.

## 2. Required endpoint contract (from parent §2.2 / §2.4)

`GET /api/order/{externalId}`

**MUST:**
1. Accept WMS's existing egress auth — `Authorization: Basic <OMS_API_USER>` + `x-tenant: <OMS_TENANT_ID>` (the same headers the outbox dispatcher / `OmsNotificationService` already send).
2. Resolve the order by its WMS-facing `externalId`.
3. Return **HTTP 200** with a JSON body containing an order **state** field (exact field name to be agreed — parent §2.2 reads `omsState`).
4. Return **HTTP 404** when the order is unknown (the parent treats 404 as drift — "OMS does not know this order").
5. Be **read-only** — no state mutation, no side effects (it runs daily across up to 10k orders/tenant).

**State values OMS must be able to report** (parent §2.4 mapping — OMS sign-off required, see row 8 of the parent's §4.1):
- For a WMS `SHIPPED` order, OMS state ∈ `{SHIPPED, DELIVERED, COMPLETED}` is consistent; anything else (or 404) is drift.
- For a WMS `CANCELLED` order, OMS state ∈ `{CANCELLED, REFUNDED}` is consistent; anything else (or 404) is drift.

## 3. Acceptance

- [ ] Route exists, auth-guarded consistently with other WMS↔OMS surfaces; accepts the Basic + `x-tenant` headers.
- [ ] 200 returns a documented JSON shape with a stable `state` field; field name agreed with WMS.
- [ ] 404 for unknown `externalId` (distinct from 5xx — WMS treats 5xx/timeout as "unreachable", not drift).
- [ ] Read-only; no mutation; safe under the daily 10k-orders/tenant read volume (parent Risk #2 — OMS GET load amplification).
- [ ] Contract documented + OMS-team sign-off recorded (parent §4.1 rows 7 & 8).

## 4. Deploy coupling (unblocks the parent)

1. Ship `GET /api/order/{externalId}` in `oms-laravel-api`; record the OMS-team sign-off (engineer + date) on the endpoint contract (parent row 7) and the §2.4 state-mapping table (parent row 8).
2. WMS implements `OmsSyncReconciliationJob` (parent §6.2) — now unblocked.
3. SRE drafts the `wms2.oms.sync.drift` alert rule (parent row 9) before the per-tenant sysprop is flipped on.

## 6. Reuse survey (Open Question 3) — 2026-07-27

Every OMS route that reads order state was enumerated (`grep -rn "Route::get" routes/ | grep -i order`, plus the
`/services/call/*` and `/v1/services/*` groups). Three near-misses, none usable as-is:

| Candidate | Auth stack | Why it does not fit |
|---|---|---|
| `POST /v1/services/call/getOrderStatus`<br>(`V1ServicesController::getOrderStatus:196`) | v1-services group: `X-API-Key` / `Authorization: Bearer` + `X-Tenant`, validated against the tenant's `external_api_keys` | **Closest semantically** — returns per-order status, batched. But: (a) **POST, not GET**; (b) requires a `clientCode` and resolves the order as `Order::where('orderID', $orderNo)->where('client_id', …)` — client-scoped, so WMS would need to know each order's OMS client code; (c) **auth mismatch** — this is *not* the `Authorization: Basic <OMS_API_USER>` + `x-tenant` egress auth the outbox dispatcher already uses; (d) unknown order returns **HTTP 200** with `statusCode: "Failure"` in the body, so the parent's "404 ⇒ drift / 5xx ⇒ unreachable" trichotomy (§2.2) has nothing to key on. |
| `GET /v1/services/v2/order/{id?}`<br>(`V1ServicesRestController::orderList`, `routes/legacy-v1-services.php:63`) | same v1-services group | `{id}` is the OMS order id, not a WMS external id. List/fetch semantics aimed at merchants (Vinoshipper/Zerolink). Same auth mismatch. |
| `GET /api/orders/{id}/status-details`<br>(`OrderStatusReportController::getOrderStatusDetails`, `routes/api.php:152`) | internal v2 API (session / JWT) | OMS-internal numeric id; internal UI surface, not an integration contract. Wrong auth entirely. |

**Conclusion: build net-new.** The cheapest shape is probably a thin `GET` sibling in the existing
`Route::prefix('services/call')` group (`routes/legacy-services.php`) — that group is where WMS↔OMS traffic already
lives, and `GET facilities` / `GET testPsd` establish that read-only GETs are acceptable there. That also
sidesteps the auth mismatch, since WMS's existing egress headers already work against that group. The trade-off is
that the group carries **no route-level middleware** (see the sibling stub's §3) — acceptable for a read-only
lookup, but call it out explicitly to the OMS team rather than letting it happen silently.

## 7. Blocker: `externalId` is ambiguous on the WMS side

The parent plan says `GET /api/order/{externalId}` and reads `order.getExternalId()`. But WMS `Customerorder`
(`v2/wms2-api/src/main/java/net/aim_ai/wms/model/Customerorder.java`) has **three** external identifiers:

| Field | Line | Notes |
|---|---|---|
| `externalnumber` | 15 | most likely intended |
| `clientordernumber` | 21 | maps most naturally to OMS `Order.orderID` + client scope |
| `parcelexternalnumber` | 24 | parcel-level, not order-level |

There is **no** field literally named `externalId`. Which one OMS can resolve — and whether resolution needs a
client scope alongside it — must be settled with the OMS team **before** the endpoint contract is agreed;
otherwise the reconciliation job will report 404-as-drift across the board on its first run. Fold this into the
parent's §4.1 row 7 sign-off.
